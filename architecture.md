> Generated by `fractal architect` on 2026-08-22.
> Stack: TypeScript + Next.js 15 (App Router, single self-hosted process) + SQLite (better-sqlite3) + Vitest + Playwright.
> Runtime AI: the `claude` CLI, one child process per module / evaluation turn, sandboxed per F6.
> Web port: **31544** (drawn randomly, recorded in `state.json.stack.ports.web`).

## Stack rationale

Self-hosted single-user website (F1–F13 are all one learner's data) with a long-running background
job engine that shells out to the Claude CLI. Next.js gives one process serving both the UI and the
API, so there is a single start command and a single port. SQLite is the only store: durable,
file-based, trivially self-hosted, and its single-writer model matches a single-user app. Generation
work is not request-scoped, so it runs in an in-process job engine (C4) backed by a durable `jobs`
table rather than inside a route handler.

**This app is offline-capable except for the Claude CLI.** Every egress row below traces to a
`claude` subprocess or to a video link the learner clicks. No telemetry, no analytics, no cloud
sync, no account system.

## C0: Cross-cutting

**Summary.** The single authority for every fact more than one component needs: the shape registry,
ID types, on-disk path derivation, configuration loading, the structured logger with its scrubber,
the error taxonomy, the compile-time release constant, and the egress matrix. It implements no
F-IDs and is built sequentially before every other component.

**Implements:** (none — infrastructure)

**Responsibilities:**
- Own every shape crossing a component boundary (§ Shape contracts below).
- Derive every filesystem path from one `appName` constant and one `dataRoot` (H10).
- Provide `log()` with an always-on scrubber applied on the last path out (H5).
- Define `IS_RELEASE` as a build-time constant so non-production surfaces tree-shake (H1).
- Define the error taxonomy: every thrown error is one named class carrying a stable `code` and a
  correlation id; raw exception text never crosses an interface (H12).
- Own the egress matrix below and the `scrub()` every egress row calls.

**Interfaces (public surface):**
- `paths(dataRoot: string) -> AppPaths` — every derived path; nothing else joins paths to the data root.
- `loadConfig() -> AppConfig` — reads env + `config.json`, maximally lenient (H13): unknown key stripped, bad value dropped to its default with a recorded `configWarnings[]`, unparseable file falls back to full defaults plus a warning. It can never prevent the Settings screen from opening.
- `log(entry: LogEntry) -> void` — writes NDJSON to `<dataRoot>/logs/app-YYYY-MM-DD.ndjson` and stderr; applies `scrub()` unconditionally.
- `scrub(value: unknown) -> unknown` — replaces learner free text with `[REDACTED:pii:<salted-digest>]`; salt is per-install, 128-bit, stored at `<dataRoot>/.scrub-salt`, never logged; digest is 128-bit (H5).
- `err(code: ErrorCode, detail: string, cause?: unknown) -> AppError` — the only error constructor. `detail` and `cause` are logged under `correlationId`; only `code` plus a stable message crosses an interface.
- `IS_RELEASE: boolean` — build-time constant, `true` in the release configuration.
- `ok<T>(data: T) -> ApiOk<T>` / `fail(e: AppError) -> ApiErr` — the two response envelopes.

**Depends on:** (nothing)
**Consumes shapes:** (none — it is the registry)

**Release surface:** production
**Excluded from release by:** n/a. `IS_RELEASE` is defined here (`false` in dev, `true` in the release build) and is the exclusion mechanism every other component names.

**Failure & recovery:**
- `config.json` unparseable → banner "Settings file could not be read; running on defaults" naming the file → full defaults loaded, `configWarnings` populated, the file is left untouched → user exit: the Settings screen, which renders from defaults and never reads the broken file (H13)
- a config key holds an out-of-range value → same banner naming the field → that one field drops to its default → user exit: Settings screen
- `.scrub-salt` missing → no user-visible effect → a new salt is minted; old digests stop correlating, no data is lost → user exit: n/a
- log directory unwritable → one stderr line, once per process, plus a Settings-screen warning → logging degrades to stderr only, the app continues → user exit: change `dataRoot` in Settings or fix permissions

**State lifecycle:**
- location: `.scrub-salt` only, beside the store (`<dataRoot>/.scrub-salt`); the database is C1's
- key custody: n/a (the salt is not a key; it is never used to decrypt anything and is never logged)
- durability: write temp → fsync → rename → fsync dir; minted once, never rotated automatically
- file mode: 0600, set on the temp file before the rename
- schema versioning: n/a (16 raw bytes)
- recovery: corrupt or short → mint a new salt and log loudly | missing → mint | newer schema → n/a

**Data & egress:**
- data classes held: `pii` (learner free text passes through `scrub()`), `internal`
- log sink ← `internal` only ← `scrub()` on every emit, always on ← on
- repository (committed files) ← `public` ← `.gitignore` covers `data/`, `logs/`, `*.ndjson`, `.env*`, `.fractal/`, `.claude/settings.local.json` ← n/a

**Trust boundaries:**
- inbound: environment variables and `config.json` ← the local user only, same trust level as the process ← n/a ← parsed leniently per H13
**Sinks:**

## C1: Store

**Summary.** The only component that touches the database. Owns the SQLite schema, the forward and
downgrade migration guards, the durable write protocol, and one repository function per aggregate
(topics, modules, edges, eval sessions, review items, reflections, predictions, jobs, source
documents). Every other component reads and writes through these functions and never composes SQL.

**Implements:** F5 (durable progress), and backs F1–F13 storage

**Responsibilities:**
- Open, migrate, and health-check `learn.db`; refuse a store whose recorded version exceeds the
  highest known migration (H4).
- Provide one transaction boundary per logical commit — module completion, availability recompute,
  and review-item scheduling all land in one transaction (F4 AC).
- Retain exactly one prior generation (`learn.db.prev`) and fall back to it on an open failure.
- Surface an unparseable topic row as a degraded record, never skip it (H4/H13).

**Interfaces (public surface):**
- `openStore(paths: AppPaths) -> Store` — ok `Store`, err `AppError` with code `store-corrupt` | `store-schema-ahead`. Runs migrations inside one transaction.
- `topics.create(input: NewTopic) -> Topic` — req `NewTopic`, ok `Topic`, err `AppError` (`validation` | `conflict`).
- `topics.get(id: TopicId) -> Topic | DegradedTopic | null`
- `topics.list() -> (Topic | DegradedTopic)[]` — one query; never N+1 over modules (H11).
- `topics.delete(id: TopicId) -> void` — reachable for a degraded topic without reading its content (H13: the recovery path does not route through what failed).
- `modules.upsertGraph(g: ModuleGraph) -> void` / `modules.graph(t: TopicId) -> ModuleGraph`
- `modules.setState(id: ModuleId, s: ModuleState) -> void`
- `evals.append(sessionId: SessionId, turn: EvalTurn) -> void` / `evals.get(id: SessionId) -> EvalSession | null`
- `reviews.due(now: ISODateString, limit: number) -> ReviewItem[]` / `reviews.upsert(item: ReviewItem) -> void`
- `reflections.*`, `predictions.*`, `calibration.*` — plain CRUD over their shapes.
- `jobs.enqueue(j: Job) -> Job` / `jobs.claimNext() -> Job | null` / `jobs.finish(id, status, error?) -> void`
- `sources.add(input: NewSourceDocument) -> SourceDocument` / `sources.listFor(t: TopicId) -> SourceDocument[]` — the index of the material a topic was built from, in the order the learner added it. The bytes live on disk under C11; this is only the record that they exist. A row that will not parse is dropped and logged, never raised: material *supplements* intake, so a bad index degrades to the no-material path rather than refusing the topic. `topics.delete` cascades these rows; the directory itself is removed by C9's delete handler.
- `completeModule(moduleId, verdict) -> { module: ModuleNode, unlocked: ModuleId[], review: ReviewItem }` — one transaction covering completion, availability recompute, and review scheduling.

**Shape contracts (owned by C1):**
- `NewTopic` = `{ subject: string, level: Level, levelDetail?: string, purpose: string, diagnostic: DiagnosticTranscript | null }`
  - example: `{ "subject": "Information theory", "level": "intermediate", "purpose": "read Shannon", "diagnostic": null }`
- `DegradedTopic` = `{ degraded: true, id: TopicId, reason: string, rawPreview: string }` — what the UI renders for a row it cannot parse, with a delete affordance (H13)
  - example: `{ "degraded": true, "id": "t_9fQ2xK4mZa71bC0d", "reason": "modules JSON failed to parse", "rawPreview": "{\"nodes\":[{\"id\"..." }`
- `StoreHealth` = `{ schemaVersion: number, highestKnownMigration: number, prevGenerationPresent: boolean, degradedTopicCount: number }`
  - example: `{ "schemaVersion": 4, "highestKnownMigration": 4, "prevGenerationPresent": true, "degradedTopicCount": 0 }`

**Depends on:** C0
**Consumes shapes:** `Topic`, `TopicNote`, `ModuleNode`, `PrereqEdge`, `ModuleGraph`, `ModuleState`, `EvalSession`, `EvalTurn`, `EvalVerdict`, `ReviewItem`, `Reflection`, `Prediction`, `Calibration`, `Capstone`, `Job`, `JobStatus`, `AppError`, `AppPaths`, `ISODateString`, `TopicId`, `ModuleId`, `SessionId` (all from C0)

**Release surface:** production
**Excluded from release by:** n/a

**Failure & recovery:**
- database file missing → no message; a fresh store is minted and the app opens empty → nothing to recover → user exit: n/a
- database corrupt / unreadable → full-screen "Your learning data could not be opened" naming the file path and the `.prev` fallback → `learn.db.prev` is loaded read-write, the corrupt file is renamed `learn.db.corrupt-<ts>`, loudly logged → user exit: an in-app "Use the previous generation" button plus the stated path; never requires a file manager
- recorded schema version exceeds the highest known migration → "This data was written by a newer version of the app" → the store is **not** opened and **not** written → user exit: install the newer version, or restore `.prev`; the message names both
- a migration throws mid-run → the transaction rolls back; neither partial schema nor the bumped version row survives → same corrupt-store screen → user exit: `.prev` fallback
- one topic row fails to parse → that topic renders as a `DegradedTopic` card marked "needs attention"; every other topic is unaffected → nothing is skipped (H4) → user exit: a Delete button on the degraded card, implemented with an id-only delete that never reads the broken content
- disk full on write → toast "Could not save — disk full", the in-memory value is retained and the write is retried on the next action → no partial row is committed → user exit: free space and retry from the same screen

**State lifecycle:**
- location: `<dataRoot>/learn.db` — Windows `%LOCALAPPDATA%\learn-assistant`, macOS `~/Library/Application Support/learn-assistant`, Linux `~/.local/share/learn-assistant`; overridable by `LA_DATA_ROOT`
- key custody: none. The store is **not encrypted**; it holds the learner's own notes on a machine they control, and there is no credential in it. This is stated plainly in the README rather than implied to be encrypted (H7). If encryption is added later it gets a real key-custody row.
- durability: SQLite in WAL mode with `synchronous=FULL`; a backup generation is produced by `VACUUM INTO learn.db.prev.tmp` → fsync → rename → fsync dir, once per app start after a successful open, and after each migration
- file mode: 0600 on `learn.db`, `learn.db-wal`, `learn.db-shm`, and `learn.db.prev`, set at creation
- schema versioning: `user_version` pragma; forward migrations in one transaction each; **downgrade guard** — refuse to open when `user_version > highestKnownMigration`; a seeded identity migration exists so the next field addition has somewhere to live
- recovery: corrupt → `.prev` fallback, loud log, corrupt file preserved | missing key → n/a (no key) | missing store → mint | newer schema → refuse to open and say so

**Data & egress:**
- data classes held: `pii` (learner free text, chat transcripts, reflections), `internal`
- SQLite store ← `pii`, `internal` ← filesystem perms, mode 0600 ← on
- log sink ← `internal` only; row contents are never logged, only ids and counts ← `scrub()` ← on

**Trust boundaries:**
- inbound: none directly — every caller is in-process. C9 is the only path from outside.
**Sinks:**
- sql at every repository function ← ids and values from callers ← **parameterised statements only**; no string interpolation into SQL anywhere; ids are re-validated against their C0 patterns at the repository boundary
- fs-path at `openStore` / backup ← `AppPaths` only ← paths come from C0's `paths()`, never from a caller

**Long-running work:**
- `VACUUM INTO` backup | max 2s at declared scale | timeout 30s | cancellable: no — it is bounded, single-shot, and off the request path (justified: interrupting a backup produces no user-visible benefit and the temp file is deleted on failure) | owner: process | on owner exit: temp file deleted | progress: none needed
- migration run | max 1s at declared scale | timeout 60s | cancellable: no (justified: a partially applied migration is worse than a slow one; it is transactional) | owner: process | on owner exit: transaction rolls back | progress: startup screen states "Upgrading your data"

**Concurrency model:** sync, called from the async event loop
**Offloaded to a thread/process:** none — the startup backup (`VACUUM INTO`) is a synchronous statement on the loop, run before the server accepts anything, so the only thing it can delay is boot; every statement on the request path is bounded (< 5ms at declared scale) and measured by the loop-blocking test
**Shared locks held:** SQLite's single write lock, held for the duration of one transaction — max hold 50ms at declared scale

**Design notes:** no UI.

## C2: AI session runner (provider abstraction + sandbox)

**Summary.** The only component that spawns a process, and the only one that knows a provider
exists. Turns a `CliSessionSpec` into one session confined to exactly one module directory, with a
timeout, a working cancel that reaches the work, a bounded tool allowlist, and a post-run
verification that nothing outside the module directory was touched. Every AI call in the app —
authoring, evaluation, review question generation, discontinuity review — goes through here.

**The provider abstraction is the point of this component.** There are eight providers and one
interface: `CliTransport` hands back a `CliChildHandle`, which is *written to*, *read from*, and
*killable* — the shape of a child process, because that is the shape the rest of C2 already knew.
The `claude` CLI implements it by being a child process. Every other provider implements it over
HTTP, and every one of those shares a single base class (`HttpChildHandle`) that owns the
pretending: buffer the prompt until stdin closes, answer in the CLI's own
`{type:"result",result:"<text>"}` envelope, report a failure as a non-zero exit with the reason on
stdout. An adapter is then a `label` and an `ask(messages) -> string` — the ten lines that are
genuinely this vendor's wire format — and nothing else. Nothing above C2 branches on provider: the
orchestrator, the evaluator and the API routes see `runSession` and a `CliSessionResult`.

**Implements:** F6

**Responsibilities:**
- Build the child's argv: `claude -p --output-format json --add-dir <moduleDir> --allowed-tools <list> --max-turns <n>`, with `cwd` set to the module directory and a minimal environment.
- Confine file access: the module directory is the only directory added; the tool allowlist excludes `Bash`, `WebFetch`, `WebSearch`, and `Task` for authoring sessions (evaluation sessions get no file tools at all).
- Snapshot the module directory (path + size + digest) before and after, and fail the session with `sandbox-violation` if any file outside it changed under `dataRoot` (verified, not just documented — F6 AC).
- Resolve the model per spawn from the session's kind: `evaluate` is the chat role, every other kind is planning (`src/core/models.ts`). The role picks the model only — the provider, and for llama.cpp the binary, stay one choice about the machine. An unset override means chat uses the planning model. For llama.cpp a chat model is a second `llama-server` on `chatModels.llama.baseUrl`, started the same way as the first; for the Claude CLI the role becomes `--model`; for every hosted provider it is the model id in the request (in the URL, for Gemini).
- Choose the transport from `AppConfig.provider`, per spawn rather than per runner, over eight choices: `claude` spawns the CLI; `ollama` and `llama` POST to a server on this machine; `openai`, `openai-compatible` and `mistral` share one adapter against `/chat/completions`; `gemini` has its own (`systemInstruction`, `contents[].parts[]`, model id in the URL, key in `x-goog-api-key`); `anthropic` uses the official `@anthropic-ai/sdk`. Every one of them answers in the CLI's own `{type:"result",result:"<text>"}` envelope, so the timeout, cancel, size cap, unwrap and schema check downstream are shared and not duplicated.
- `openai-compatible` is a first-class provider, not a special case: a base URL the learner sets, an optional key, and a retry that drops `response_format` and `temperature` when a server refuses them. That is what makes LM Studio, vLLM, llama.cpp's own server, OpenRouter, Groq, Together and DeepSeek reachable without an adapter each — and without a table of who supports what, which would be stale the week it was written.
- Give a provider with no file tools the same file-scoped authoring the CLI gets: read the module directory in, put it in the prompt, take the model's files back out and write them through the same confinement (`src/cli/workspace.ts`, called by `spawnAndWait` around the transport). This is one mechanism for all seven non-CLI providers, gated on `hasFileTools(provider)` — true only for `claude` — because six copies of a path check is six chances to miss `..`.
- Read a hosted provider's API key only through `src/core/keys.ts` (C0), per request, never holding it on a client or in `AppConfig`. A missing key fails the session before any request is sent, naming the variable to set.
- Enforce the timeout and the stall watchdog; kill the child's whole process group on cancel (for every HTTP provider, abort the request — a local model left generating holds the machine's GPU, and a hosted one left generating is still being billed).
- Hold the app's only concurrency limit: `config.sessionConcurrency` permits over every session, whatever asked for it. It is a queue, never a refusal — work over the limit waits and then runs. This is here and not in a caller because the runner is the one place that sees every session, and the reason for the limit is load on one provider, not permission.
- Put one spawn per turn of the event loop. A wide pool takes its permits in a single tick, so a
  fan-out spawned every one of its children inside one turn and the app served nothing until the
  burst was over. Child processes are heavy and largely synchronous; the sessions they start run for
  minutes, so serialising the spawn itself costs a swarm nothing measurable.
- Order that queue by who is waiting on it. A `chat`-role session (`evaluate`, `ask` — a turn a learner is sitting in front of) goes ahead of queued background work and may take one permit above the limit; everything else keeps the limit unchanged and is only ever overtaken by those few turns. Without this a learner's answer waits out an entire `generate-topic` fan-out — every unwritten module of a topic, queued at once, minutes each.
- Return `CliSessionResult`; never let raw stderr cross the interface (H12).

**Interfaces (public surface):**
- `runSession(spec: CliSessionSpec, signal: AbortSignal) -> Promise<CliSessionResult>` — req `CliSessionSpec`, ok `CliSessionResult` (`ok: true`), err `CliSessionResult` (`ok: false`). Never throws.
- `checkCli() -> CliAvailability` — probes the selected provider once at startup, **after** the server binds (H15): `claude --version` for the CLI, `GET /api/tags` for Ollama (which also checks the configured model is pulled, because a reachable server missing it fails every session instead), and for a hosted provider the vendor's own model list — which proves reachable, key accepted and model offered without spending a generation. A provider with no key set is reported as unusable naming the variable, and nothing is dialled.
- `testProvider() -> ProviderTestResult` (behind C9's Settings route) — one cheap real call through the *same* `transportFor` a session uses, so a pass means a session would pass. A side-channel probe could succeed against a provider the runner cannot actually drive.
- `buildPrompt(ctx: ModuleBrief) -> string` — the single place a module brief becomes prompt text, so every caller sends the same text (H8).

**Shape contracts (owned by C2):**
- `ModuleBrief` = `{ topicSubject: string, level: Level, levelDetail: string | null, purpose: string, drivingQuestion: string, moduleTitle: string, moduleObjectives: string[], prerequisiteSummaries: { title: string, oneLine: string }[], downstreamSummaries: { title: string, oneLine: string }[], priorKnowledge: string[], targetMinutes: number }`
  - example: `{ "topicSubject": "Information theory", "level": "intermediate", "levelDetail": null, "purpose": "build a compressor", "drivingQuestion": "How small can a message get?", "moduleTitle": "Entropy as expected surprise", "moduleObjectives": ["Define entropy"], "prerequisiteSummaries": [{ "title": "Probability refresher", "oneLine": "Distributions and expectation." }], "downstreamSummaries": [], "priorKnowledge": ["basic probability"], "targetMinutes": 20 }`
- `CliAvailability` = `{ available: true, version: string } | { available: false, reason: "not-found" | "not-executable" | "probe-failed", hint: string }`
  - example: `{ "available": false, "reason": "not-found", "hint": "Install the Claude CLI and ensure `claude` is on PATH, or set LA_CLAUDE_BIN." }`
- `SandboxSnapshot` = `{ files: { relPath: string, size: number, digest: string }[], takenAt: ISODateString }`
  - example: `{ "files": [{ "relPath": "content.json", "size": 1421, "digest": "b1946ac9…" }], "takenAt": "2026-08-22T09:20:00.000Z" }`

**Depends on:** C0
**Consumes shapes:** `CliSessionSpec`, `CliSessionResult`, `SessionId`, `Level`, `AppError`, `AppPaths`, `ISODateString` (from C0)

**Release surface:** production
**Excluded from release by:** n/a. The `LA_FAKE_CLI` transport used by tests lives in `src/cli/transport.fake.ts` and is **test-only**, excluded by `IS_RELEASE` (dead-code eliminated) — and its selection compares `process.env.LA_FAKE_CLI === "1"` exactly, never definedness (H1).

**Failure & recovery:**
- `claude` binary not found → a persistent banner "The Claude CLI is not installed or not on PATH", with the exact install command and the `LA_CLAUDE_BIN` override → no session is dispatched; the topic stays `queued`, nothing is marked failed → user exit: install, then a "Retry" button on the topic
- session exceeds its timeout → the module shows "Authoring timed out", the topic goes `needs-attention` → the child's process group is killed, partial files in the module dir are discarded, the job is retryable → user exit: a "Retry this module" button
- child writes outside the module directory → the session fails with `sandbox-violation`; the module shows "Authoring session was blocked" → every file the session wrote is reverted from the pre-run snapshot, the violation is logged with the offending relative path → user exit: Retry
- child exits non-zero → "Authoring failed" plus the stable message → stderr is logged under a correlation id, never surfaced verbatim → user exit: Retry, and the log path is shown
- child produces unparseable output → treated as `nonzero-exit`; the raw output is logged, not shown → user exit: Retry
- child runs out of context → `context-exhausted`; the module is marked `needs-attention` per F2 → partial content is discarded → user exit: Retry (the brief is trimmed on the retry)
- cancel requested → the module returns to its previous state → the process group is killed and awaited, the in-flight flag is cleared in a `finally` → user exit: n/a

**State lifecycle:** does not own persistent state. It writes only inside `moduleDir`, which C1/C4 own.

**Data & egress:**
- data classes held: `pii` (the brief contains the learner's purpose and prior-knowledge statements) — held transiently for the duration of one session
- `claude` CLI subprocess (argv + stdin) → Anthropic API ← `pii`, `internal` ← the learner's press on the control that asked for the work; the sandbox and the `sessionConcurrency` limit bound it ← **on** (single-user local app)
- Ollama / llama.cpp server on `127.0.0.1` (prompt in the request body) ← `pii`, `internal` ← same press; only when the provider is `ollama` or `llama` ← off (provider defaults to `claude`) — nothing leaves the machine
- OpenAI-compatible endpoint (`<baseUrl>/chat/completions`) ← `pii`, `internal` ← same press; only when the provider is `openai`, `openai-compatible` or `mistral`. Whether this leaves the machine is `leavesThisMachine()` on the configured base URL, not a fixed property of the provider — an `openai-compatible` pointed at `127.0.0.1:1234` goes nowhere ← off
- Google Gemini (`<baseUrl>/models/<id>:streamGenerateContent`) ← `pii`, `internal` ← same press; only when the provider is `gemini` ← off
- Anthropic API direct (`<baseUrl>/v1/messages`, via `@anthropic-ai/sdk`) ← `pii`, `internal` ← same press; only when the provider is `anthropic` ← off
- module directory ← `pii`, `internal` ← path confinement ← on
- log sink ← `internal` only: session id, kind, duration, exit code, file count. **Prompt text and model output are never logged**, only their byte lengths and a digest. **No API key is ever logged**: a key is read at the moment of use, never lands in `AppConfig`, and every key variable name is covered by `scrub()` ← `scrub()` ← on

**Trust boundaries:**
- inbound: the session's **output** ← the Claude CLI or a provider's HTTP response, i.e. model-generated content ← not authenticated, and treated as untrusted data: parsed against the module-content schema, never `eval`'d, never used to build a path, and rendered as Markdown with HTML disabled and a strict sanitizer (C10)
- inbound: the session's **file writes** ← model-generated ← for the CLI, confined to `moduleDir` by `--add-dir`; for every other provider the model names a relative path in its answer and `takeWorkspaceWrites` resolves and rejects it before anything is written. Both are then held to the same post-run snapshot diff; a symlink inside the module dir pointing outside it is detected by resolving every written path before comparison
- inbound: the provider's **base URL** ← `AppConfig`, from Settings or `LA_<PROVIDER>_URL` ← validated as a URL before it is stored; it is a request target only, never a path and never a shell word
**Sinks:**
- exec at `spawn(claudeBin, argv)` ← `claudeBin` from **config only, never from a caller or a wire value** (H12: a stored setting outranks a wire value); argv is a fixed array, never a shell string; `shell: false` always

- deserialize at `JSON.parse(childStdout)` ← model output ← size-capped at 1 MB, parsed then validated against the `ModuleContent` guard; a failure is `nonzero-exit`, never a partial write

**Long-running work:**
- `runSession` (authoring) | max 300s | timeout 600s, plus a 90s no-output stall watchdog | cancellable: `AbortSignal` → `SIGTERM` to the process group, `SIGKILL` after 5s, awaited | owner: the job (C4) | on owner exit: cancel | progress: bytes-since-last-tick emitted to C4, so a stalled session is distinguishable from a slow one
- `runSession` (evaluation turn) | max 60s | timeout 120s, 30s stall watchdog | cancellable: same | owner: the HTTP request / eval session | on owner exit: cancel | progress: token stream ticks
- `checkCli` | max 2s | timeout 5s | cancellable: yes | owner: process | on owner exit: cancel | progress: n/a

**Concurrency model:** async event loop
**Offloaded to a thread/process:** the child process itself, and nothing else — the snapshot digest walk is a synchronous hashing loop over one module directory, bounded by what a single module holds
**Shared locks held:** a per-module mutex, so two sessions never target one module directory — max hold: one session's timeout, released by cancellation; and a process-wide semaphore of `config.sessionConcurrency` permits over every spawn (plus one reserved permit that only a learner-facing `chat`-role session may take)

**Design notes:** no UI. Every spawned child is registered in a live set and strongly referenced until it exits (H14); the set is drained on process teardown.

## C4: Curriculum orchestrator

**Summary.** The job engine and the generation pipeline. Turns a queued topic into a module graph:
research the outline and driving question, fan out one sandboxed authoring session per module,
author the capstone spec, then run the single discontinuity review. Also owns detour insertion and
whole-course extension (F12), and the remedial mini-module request from C6.

**Implements:** F1 (job kickoff), F2, F12

**Responsibilities:**
- Own the durable job queue: claim, run, retry-once, and mark `failed` with a retryable status.
- Run the research session, producing the driving question and a **graph** proposal — prerequisite
  edges only where genuine, preferring wide over deep.
- When the learner brought material (C11), hold the graph to it **as evidence, not as gospel**. The
  research still runs; the material bounds what it may return. Concretely: `unitFloor()` raises the
  module count so the syllabus's units cannot be squeezed out by an estimate, every named unit is
  checked against the outline that comes back with a token-overlap test, and a unit nothing covers
  is **inserted** in the material's own order — displacing filler from the tail when the model
  filled every slot — rather than reported as a gap. A prerequisite the material never names is
  still added where the subject needs one, because a syllabus states what a course covers and not
  what a reader must already know. Each authoring session is handed the excerpts matching its own
  module, so lessons use the material's vocabulary. When research returns nothing usable *and*
  material exists, the material's own units become the plan, in preference to the generic
  subtopic fallback.
- Fan out authoring sessions straight to C2, each writing only its own module directory. The
  fan-out is unbounded here on purpose: C2 holds the one concurrency limit, so a second one at this
  layer would only be a place for the two to disagree.
- Prepare one **prep window** per authorised pass, not the whole plan: the lessons the learner can
  start now first, then the unwritten lessons within `PREP_LOOKAHEAD_DEPTH` prerequisite layers
  behind them, capped at `MAX_PREP_MODULES` — sized to a whole ordinary topic, because the next pass
  is only picked up by the five-minute sweep and a window narrower than C2's session pool leaves most
  of that pool idle in between. Availability comes before ordinal in that ordering, or
  a full window of locked lessons can crowd out the unlocked one the pass was queued for and the
  sweep re-queues the same window forever. The plan itself is uncapped — "high school biology to MCAT-ready" is a
  degree's worth of lessons and is allowed to be — but writing all of it before the first lesson is
  read spends every session up front on material the learner may never reach. The window slides
  forward as lessons land, and the topic page offers the next pass.
- Drain up to `MAX_CONCURRENT_JOBS` jobs beside each other rather than one at a time. Jobs are
  independent — a second subject's research has nothing to do with the first subject's authoring —
  and draining them in sequence made the second subject wait out the first subject's entire course
  with permits going spare. What they may spend is still bounded underneath by `sessionConcurrency`;
  this is only how many may be in the air. `claimNext` is a single synchronous claim, so two workers
  can never take one job.
- Keep partial modules when a session fails; mark the topic `needs-attention` and offer per-module retry.
- Treat `needs-attention` as one attempt's mark, not a diagnosis: the prep sweep retries such a
  subject in the background up to `MAX_RECOVERY_ATTEMPTS` consecutive passes, since the pass is
  itself the repair — it retires the failure notes for the lessons it rewrites and re-runs the
  consistency check. The count lives in C4's sidecar (`prepAttempts`) so it survives a restart, any
  pass that writes a lesson clears it, and the learner asking for a pass themselves clears it too.
- Run the discontinuity review **exactly once** per set of lessons, on the pass that finishes the
  course — it reads the course as a whole, and on a partially prepared one every lesson a later pass
  is about to write comes back as a gap. It validates the graph (acyclic, ≥1 entry module, no
  unreachable node) and cross-topic connections.
- **Resolve** what the review finds rather than reporting it: route each finding to the lesson it
  names, rewrite those lessons with the finding attached, re-run the check, up to
  `MAX_REPAIR_ROUNDS` times. Produce `TopicNote`s only for what the learner can act on — a
  cross-topic connection to make, a check that could not run, a lesson that could not be written.
- Insert a detour node without renumbering and without ever making it a prerequisite of an existing module.
- **Extend an existing course to a further goal** ("Practical Biology" carried to "sufficient
  knowledge for the MCAT"). One research pass, briefed with the lessons the course already has —
  each summarised by its first learning goal, because a title does not say how far the course took
  the learner and the only judgement this pass makes is what is MISSING. What comes back is deduped
  against the existing titles here as well as asked for in the prompt, sized to `extensionSize(goal)`
  (the plan's own breadth measure, floored at `MIN_EXTENSION_MODULES` and — unlike a plan — capped at
  `MAX_EXTENSION_MODULES`), appended past every existing ordinal, hung off the course's frontier, and
  the capstone re-hung behind it. The pass ends exactly where research ends: `needs-attention`, with
  the new lessons unwritten and the prep-window control offering to write them. The goal itself rides
  in C4's sidecar (`extensions`), not on the job row — a job carries a topic and a module and nothing
  else — which is also what puts a request that has not been planned yet on the subject's page.

**Interfaces (public surface):**
- `enqueueTopic(topicId: TopicId) -> Job` — ok `Job`, err `AppError` (`validation` | `conflict`).
- `resumeGeneration(topicId: TopicId) -> Job` — the next prep pass; err `AppError` (`conflict` before the outline exists).
- `planFor(input: NewTopic) -> GenerationPlan` — the deterministic session-count estimate the topic page quotes; no dispatch.

**Release surface:** production
**Excluded from release by:** n/a

**Failure & recovery:**
- research session fails → "Could not research an outline for this subject" → falls back to a generic decomposition by subtopic (an F2 path), topic continues → user exit: proceed, or delete the topic
- one authoring session fails or times out → that module card reads "Authoring failed"; the topic goes `needs-attention` → every other module is kept and usable → user exit: "Retry this module", or "Continue without it"
- every authoring session fails → topic `needs-attention` with the shared cause named once (e.g. CLI missing) → nothing partial is presented as complete → user exit: fix the named cause, then "Retry topic"
- discontinuity review finds a gap → the lessons it names are rewritten with the finding attached and the check runs again, for up to `MAX_REPAIR_ROUNDS` rounds of `REPAIR_TARGETS_PER_ROUND` lessons → the topic flips to `ready` when the loop converges; nothing about the seams is shown, because a pedagogical defect in work the app did is not something the reader can act on → user exit: none needed
- the repair loop runs out of rounds, or a finding names no lesson this topic has → what is left is logged as `curriculum-repair-unresolved` and the topic is `ready` → the lessons are all still the lessons that were there → user exit: none needed
- discontinuity review itself fails → topic is `ready-with-notes` carrying one note "consistency check could not run" → modules are not blocked → user exit: "Run the check again"
- the graph comes back cyclic → the cycle is broken by dropping the lowest-confidence edge, and `curriculum-graph-repaired` in the log names exactly which edge was dropped → never silently accepted, and never shown: by the time anything renders, the graph IS the corrected graph → user exit: none needed
- detour requested while the topic is `needs-attention` → declined with the reason stated ("finish or retry the failed module first") → nothing is queued → user exit: retry the failed module
- process restarts mid-generation → the topic shows "Resuming" → jobs left `running` at boot are reset to `queued` (attempts preserved), and the module directories are cleaned back to their last committed state → user exit: automatic; the Stop button remains available

**State lifecycle:**
- location: module directories under `<dataRoot>/topics/<topicId>/modules/<moduleId>/`; the graph and job rows live in C1
- key custody: n/a
- durability: a module is committed by writing `content.json` (temp → fsync → rename → fsync dir) **and then** inserting the module row in C1 in one transaction that also records the content digest. The row is written **second**, and the loader keys discovery on the **row**, so an interruption in the gap leaves an orphan directory, never a module the reader silently skips (H4). A startup sweep reconciles orphan directories against rows and rebuilds the row from `content.json` when the digest validates.
- file mode: 0600 on files, 0700 on module directories
- schema versioning: `content.json` carries `contentVersion`, compared on read; a newer version is a degraded module with a named reason, never a silent load
- recovery: corrupt `content.json` → the module renders degraded with a Retry affordance | missing directory but present row → the module is marked `needs-attention` and is retryable | present directory but missing row → rebuilt if the digest validates, else deleted on the learner's confirmation | newer `contentVersion` → degraded, "written by a newer version"

**Data & egress:**
- data classes held: `pii` (purpose, diagnostic transcript, prior knowledge — all fed into briefs)
- `claude` CLI subprocess ← `pii`, `internal` ← **via C2 only** ← on
- module directories ← `pii`, `internal` ← path confinement ← on
- log sink ← `internal`: job ids, kinds, durations, module counts. Never brief or content text ← `scrub()` ← on

**Trust boundaries:**
- inbound: enqueue/retry/detour calls ← the local browser via C9 ← bearer token ← single-user
- inbound: **model-authored content** ← the Claude CLI ← untrusted: `content.json` is validated against the `ModuleContent` guard before any row is written; `Explanation.url` is accepted only if it parses as `https:` with a host in the video-host allowlist, otherwise the explanation is coerced to `kind: "text"`; every module id referenced in a proposed edge must already exist in this topic
**Sinks:**
- fs-path at the module directory writer ← `TopicId`, `ModuleId` from the store (never from model output) ← C0's `moduleDir()` pattern validation plus a resolved-path containment assertion
- url at the video-link validator ← `Explanation.url` from model output ← `https:` only, host allowlist (`youtube.com`, `youtu.be`, `vimeo.com`), no credentials in the URL, no private ranges; the app never fetches it — the learner clicks it
- deserialize at `content.json` read ← model-written file ← 1 MB cap, schema-validated, never `eval`'d

**Long-running work:**
- `generate-topic` (whole pipeline) | max 20 min at declared scale (the F2 budget) | timeout 60 min overall, with per-session timeouts from C2 | cancellable: yes — `AbortController` per job, threaded into C2's child kill | owner: the job row; the job engine is the process-level owner | on owner exit: in-flight jobs are cancelled and reset to `queued` at next boot | progress: `GenerationProgress` with `modulesDone` and `lastTickAt`, so the UI distinguishes stalled from slow
- `discontinuity-review` | max 5 min | timeout 10 min | cancellable: yes | owner: the job | on owner exit: cancel, topic stays `ready-with-notes` pending the re-run | progress: phase tick

**Concurrency model:** async event loop
**Offloaded to a thread/process:** every model call is already a child process; nothing else leaves the loop — graph validation (topological sort, reachability) and content digesting both run inline, bounded at `scale: modules per topic=12` and by the size of one module of content
**Shared locks held:** a per-topic mutex around graph mutation (insert detour, commit module) — max hold < 20ms. Authoring sessions hold no lock here; C2's `sessionConcurrency` semaphore is the only limit on them

**Design notes:** no direct UI; it feeds C10 through C9's SSE stream.

## C5: Module graph service

**Summary.** All graph logic in one place: availability derivation from prerequisite edges, the
advisory-not-blocking entry rule, test-out eligibility, unlock propagation on completion, and the
topic-status roll-up (`modules-complete` vs `done`). Pure functions over a `ModuleGraph` plus thin
store calls — no model access, no I/O beyond C1.

**Implements:** F3 (availability + advisory prereqs + test-out), F5 (progress roll-up), F12 (insertion validity)

**Responsibilities:**
- Derive `ModuleState` for every node from completion records and prerequisite edges.
- Compute `unlocked` sets on completion, in the same transaction as the completion (C1.`completeModule`).
- Enforce that prerequisites are **advisory**: `canEnter()` always returns enterable, with a
  `warning` naming the unmet prerequisites — never a hard block (F3 AC).
- Validate a proposed insertion: acyclic after insertion, and the new node is not a prerequisite of
  any pre-existing node (F12 AC).
- Roll up topic status: all modules passed → `modules-complete`; capstone passed → `done`.
- Express progress with no numeric or letter grade anywhere (F5 AC) — counts of open/completed only.

**Interfaces (public surface):**
- `availability(g: ModuleGraph, completed: Set<ModuleId>) -> ModuleAvailability[]`
- `canEnter(g, moduleId, completed) -> EntryDecision` — always `{ enterable: true, ... }`; carries the advisory when prerequisites are unmet.
- `unlockedBy(g, moduleId, completed) -> ModuleId[]`
- `validateInsertion(g, node: ModuleNode, edges: PrereqEdge[]) -> InsertionCheck`
- `topicRollup(g, completed, capstoneStatus) -> TopicStatus`
- `dashboard() -> DashboardView` — one query per section, never per topic (H11).

**Shape contracts (owned by C5):**
- `ModuleAvailability` = `{ moduleId: ModuleId, state: ModuleState, unmetPrereqs: ModuleId[] }`
  - example: `{ "moduleId": "m_71bC0d9fQ2xK4mZa", "state": "available", "unmetPrereqs": [] }`
- `EntryDecision` = `{ enterable: true, advisory: { unmetPrereqs: { id: ModuleId, title: string }[] } | null }`
  - example: `{ "enterable": true, "advisory": { "unmetPrereqs": [{ "id": "m_0d9fQ2xK4mZa71bC0", "title": "Probability refresher" }] } }`
- `InsertionCheck` = `{ ok: true } | { ok: false, reason: "would-create-cycle" | "prereq-of-existing" | "unknown-anchor", detail: string }`
  - example: `{ "ok": false, "reason": "prereq-of-existing", "detail": "A detour may not become a prerequisite of module 3." }`
- `DashboardView` = `{ topics: { id: TopicId, subject: string, status: TopicStatus, completedCount: number, availableCount: number, remainingCount: number, capstone: "not-started" | "in-review" | "passed" | "n/a", needsReviewCount: number, assistedPassCount: number }[], reviewsDue: number, synthesisAvailable: boolean }`
  - example: `{ "topics": [{ "id": "t_9fQ2xK4mZa71bC0d", "subject": "Information theory", "status": "ready", "completedCount": 3, "availableCount": 2, "remainingCount": 7, "capstone": "not-started", "needsReviewCount": 0, "assistedPassCount": 1 }], "reviewsDue": 4, "synthesisAvailable": false }`

**Depends on:** C0, C1
**Consumes shapes:** `ModuleGraph`, `ModuleNode`, `PrereqEdge`, `ModuleState`, `ModuleId`, `TopicId`, `TopicStatus`, `AppError` (C0)

**Release surface:** production

## C6: Evaluation engine

**Summary.** Every Socratic chat in the app: module evaluation, test-out entry, the graduated-hint
ladder, teach-back, the remedial trigger, cross-topic synthesis (F9), and capstone work-review
(F13). Owns the evaluator prompt contract, the verdict parsing, the assist-level record, and the
re-ask-from-a-different-angle rule.

**Implements:** F3 (the mid-lesson question), F4, F9, F13

**Responsibilities:**
- Open, resume, and persist `EvalSession`s turn by turn, so a chat abandoned mid-way resumes exactly.
- Run one C2 evaluation session per learner message.
- Answer a question the learner asks *while reading* a lesson (F3): a single `ask` session bounded
  by the same `taughtScope` the evaluator is bounded by, with no verdict, no session row, no assist
  level and no effect on completion. The exchange is written back through C8 as a marked note, so a
  revisit shows what was already asked without a table of its own.
- Enforce the hint ladder: a struggling answer gets escalating hints (assist level 1→3) before a
  `fail`; a pass earned at assist level ≥2 is persisted as `assisted-pass`. Mid-conversation the
  evaluator's self-reported assist level may rise by at most one rung per turn, so no single turn
  jumps the ladder and forecloses a clean pass; the level reported on the passing turn is taken as
  given, because that is the accounting of what the whole exchange cost.
- Open the chat with a message addressed to the learner: `seedQuestions[0]` is sent verbatim, so a
  seed written as a stage direction to a tutor ("Hand the learner...") is re-addressed to them
  first, falling back to a learner-facing sibling seed and then to the generic opener.
- Keep one live conversation per lesson: on the first learner message, any sibling session on the
  same module still sitting at its opening question is closed as superseded. Reopening that gate
  revives it with a fresh opening question; a conversation the learner has spoken in is never
  closed this way.
- Enforce non-repetition: a re-ask must use an `angle` not already used in this session, and its
  text must not be a near-duplicate of a prior question (normalized-similarity check, not a promise).
- Run teach-back as a preferred remedial angle: the evaluator plants a specific misconception from
  the module's `EvalScript`; the exchange passes only if the learner names and corrects it.
- Trigger a remedial mini-module through C4 after 3 consecutive failures on the same concept — never
  loop the same question without new instructional input.
- On pass, call C1's `completeModule` so completion, unlock, and review scheduling are one transaction.
- On a **review** target whose hint ladder is exhausted, report the failed retrieval to C7. This is
  the one review outcome `completeModule` never sees, since that transaction refuses a non-passing
  verdict. Fires once per session, on the first terminal `fail`.
- Synthesis (F9): name both topics explicitly in the question; the verdict never affects either
  topic's own completion state.
- Capstone (F13): review the submitted artifact, not recall; keep every prior round's feedback visible.

**Interfaces (public surface):**
- `open(kind, target: EvalTarget) -> EvalSession` — err `AppError` (`not-found`).
- `send(sessionId: SessionId, message: LearnerMessage) -> EvalTurnResult` — ok `EvalTurnResult`, err `AppError` (`cli-failed` | `timeout`).

## C7: Review scheduler & interleaved practice

**Summary.** The spaced-repetition scheduler (F7) and the interleaved practice session builder
(F8). Owns the memory model, the mapping from our outcomes onto its grades, the due queue, and the
mixing rule that guarantees a practice session never draws entirely from one topic when two are
available.

The interval algorithm is **FSRS-6** via `ts-fsrs`, not a hand-rolled SM-2 ease multiplier. Why
that algorithm, what our evaluator-judgement signal does and does not map onto, and what we
declined to adopt from the FSRS ecosystem is argued in
[`docs/spaced-repetition.md`](docs/spaced-repetition.md) - read it before changing the grade
mapping.

**Implements:** F7, F8, F14

**Responsibilities:**
- Own the memory model in `src/review/memory.ts`: a pure wrapper over `ts-fsrs` with no store and
  no clock of its own, so C1's `completeModule` transaction can call it without a dependency cycle
  and so scheduling is deterministic and testable with no provider call. Interval fuzz and
  short-term (sub-day) learning steps are both off.
- Map our outcomes onto FSRS grades. This is the component's central design decision, not a
  detail: `Good` for a clean or lightly-hinted outcome, `Hard` for an `assisted-pass` or any pass
  at assist level ≥2, `Again` for a failed retrieval. **`Easy` is never emitted from any input.**
- Schedule a `ReviewItem` on every module completion. The first interval is *derived* from the
  grade rather than configured — `Good` → 3 days, `Hard` → 2 days — so F7's rule that an
  assisted pass is scheduled earlier is a property of the model, and it persists into later
  intervals because `Hard` also raises initial difficulty. A completion is graded as an encoding
  event and never records a lapse.
- Advance intervals on a graded retrieval, capped at 180 days. A module **never graduates out** of
  scheduling — the cap is a maximum interval, not an exit. A miss sets `flaggedNeedsReview: true`,
  increments `lapses`, and moves the module to `needs-review`; it does not reset the interval to a
  beginner's, because FSRS's post-lapse stability remembers how strong the memory was, and it does
  not penalise the item forever, because difficulty mean-reverts.
- Register a miss from either route a review can fail by: the queue card's "I had forgotten this",
  and a review taken through C6's evaluator chat whose hint ladder runs out. The second is the only
  review outcome that does not travel through `completeModule`, which refuses a non-passing verdict,
  so C6 calls `recordGradedReview` directly — once per session, on the first terminal `fail`.
- Keep the memory model **internal**. `ReviewItem` carries `memory: ReviewMemory`
  (stability/difficulty/reps/last-reviewed); what crosses C9 is `ReviewCue`, narrowed by the single
  function `toCue`. Retrievability is computed for ordering and logging and is never returned to a
  caller. F5 forbids progress expressed as a grade, and these are exactly the numbers a dashboard
  would be tempted to render.
- Carry an existing learner across the upgrade: schema migration v5 reads each row's stored
  `interval_days` and `ease` into a DSR state (stability from the interval, difficulty interpolated
  between `ease`'s two fixed points) rather than resetting anyone's schedule.
- Generate the review question through C6's evaluator contract, reworded from the module's
  `EvalScript` and never a verbatim repeat.
- Surface the due queue on the dashboard as a **queue, not a gate** — missing reviews blocks nothing.
- Build an interleaved session: at most `ceil(n/2)` questions from any one topic when ≥2 topics
  have completed modules; fall back to single-topic practice with no error when only one qualifies.
- Batch the backlog: due items are drawn at `REVIEW_DAILY_CAP` (200), never all at once. The cap is this component's own reading limit, not a spend gate.

**Interfaces (public surface):**
- `scheduleOnCompletion(moduleId: ModuleId, assist: AssistLevel) -> ReviewItem`
- `due(now: ISODateString, limit: number) -> ReviewItem[]`
- `startReview(moduleId) -> EvalSession` — delegates to C6 with `kind: "review"`.
- `recordGradedReview(moduleId, grade: ReviewGrade) -> ReviewItem` — the full-signal path, used by C6.
- `recordReview(moduleId, correct: boolean) -> ReviewItem` — the binary path (queue card, F8 practice answer); a binary signal carries nothing that could distinguish `Hard` from `Good`, so it does not pretend to.

  - example: `{ "requestRetention": 0.9, "maxIntervalDays": 180, "minIntervalDays": 1 }`

  - example: `{ "stability": 2.3065, "difficulty": 2.1181, "reps": 1, "lastReviewedAt": "2026-08-25T00:00:00.000Z" }`

### The flash card library (F14)

The one part of this app where recall *is* the material. It reuses the memory model above
wholesale — `src/cards/library.ts` calls the same `firstSchedule` / `nextSchedule` as a module
review does, at the same request retention, with the same three grades — and adds nothing to it.
What differs is only the signal: a module's grade is an evaluator's judgement of understanding, a
card's is the learner pressing one of three buttons, which is the ordinary flashcard self-grade
FSRS was built for and is therefore the *least* strained use of it in this codebase.

- `src/cards/parse.ts` reads a pasted list into cards, splitting each line on the first separator
  it recognises (tab, spaced dash, pipe, spaced equals, colon — longest and least ambiguous first,
  so `Carboxyl — -COOH` splits on the spaced dash and not on the dash inside the formula). A line
  it cannot split is returned in `skipped`, never guessed at and never dropped.
- `src/cards/library.ts` owns deck and card operations, the study queue (everything due, soonest
  first, which puts a card added a minute ago ahead of one that came round again today) and
  `gradeCard`. A card with `reps = 0` has never been answered, so its first grade goes through
  `firstSchedule`; every later one through `nextSchedule`.
- `toCardView` is the boundary. It is the same rule `ReviewCue` follows: stability, difficulty and
  retrievability order the queue and never leave the process. What the browser receives is the
  card's two sides, when it is next due, and whether it has ever been answered.
- Editing a card's text goes through C1 without touching the schedule columns — a correction is not
  a retrieval.
- `importCardPack` is the F14 x F2 seam: the cards a lesson wrote for itself (`ModuleContent.cardPack`,
  authored by C4's module session and validated with the rest of the lesson) become a real deck the
  moment the learner asks for them, and not one moment earlier. It is deliberately idempotent — it
  reuses the deck of that name on that subject and skips any card whose front is already in it — so
  pressing the button again means "make sure these are in my cards" and never "reset the schedules
  I have earned". The pack is read from the stored lesson by `POST /api/modules/:id/cards`, never
  from the request body: the cards were checked on the way in, and taking a list from the browser
  here would turn a one-button import into an unvalidated write path into the library.

**Files:** `src/cards/parse.ts`, `src/cards/library.ts` (deck/card operations, the study queue,
`gradeCard`, `importCardPack`, `findPackDeck`), `app/api/cards/**`, `app/api/modules/[id]/cards/route.ts`
(C9: the one-button pack import), `src/ui/components/CardStudy.tsx`, `src/ui/components/CardPackPanel.tsx`
(C10: the pack as the lesson offers it), `src/ui/cards-copy.ts`.

**Tests:** `tests/cards/library.test.ts`, `tests/cards/parse.test.ts`, `tests/cards/pack.test.ts`
(unit, covers the lesson pack: a deck on the subject, a second take that adds and moves nothing, a
rewritten lesson's extra cards, and a pack nobody asked for staying unmade), `tests/ui/cards.test.tsx`,
`tests/ui/card-pack.test.tsx`, `e2e/f14-flashcards.spec.ts`, `e2e/f14-lesson-cards.spec.ts`.

sides, it belongs to a deck, and a deck may belong to no subject at all.

## C9: HTTP API

**Summary.** The only inbound surface. Next.js route handlers under `/api/*` plus one SSE endpoint,
each a thin adapter: authenticate, validate the request body against its C0 shape, call exactly one
service function, wrap the result in `ApiOk`/`ApiErr`. No business logic lives here.

**Implements:** F1 (intake endpoint), and the transport for F2–F13

**Responsibilities:**
- Enforce the **per-launch bearer token** on every route including the SSE stream — loopback is not
  authentication (H12). The token is minted at startup, written to `<dataRoot>/.session-token`
  (mode 0600), and injected into the served HTML so the app's own page has it and a foreign page
  does not.
- Reject any request whose `Origin`/`Host` is not the configured origin, explicitly — deny by default.
- Validate every request body against its declared shape before it reaches a service.
- Convert an `AppError` into a status + `ApiErr`; never serialize a stack, a filesystem path, or the
  offending input (H12). The correlation id in the response is the key into the log.
- Set security headers: `Content-Security-Policy` with no `unsafe-inline` script source and no
  remote script origins, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`,
  `frame-ancestors 'none'`. The policy is defined once in `src/core/csp.ts` and applied twice:
  API JSON/SSE responses get the locked-down form from `src/api/respond.ts`, and HTML documents
  get it from `middleware.ts` with a per-response `script-src` nonce (Next's App Router streams
  its payload through inline `<script>` tags, and a nonce is what lets those run while an
  injected one does not) plus `style-src 'unsafe-inline'` for KaTeX's inline style attributes.
  A document CSP matters because the served HTML carries the session token in a `<meta>` tag and
  renders model-authored markup — it is the second line of defence behind the C10 sanitizer.

**Interfaces (public surface):**
- `POST /api/source` — req **either** `multipart/form-data` with one `file` part **or** JSON `{ text }`, ok `ApiOk<StagedSource>`, err `ApiErr` (`validation`). Reads one piece of material and hands back what it says about itself, so the form can pre-fill the subject before there is a topic to file it under. One route for both shapes because they are one operation differing only in how the bytes arrived. Dispatches **no** session: extraction is local and free. The declared size is refused before the body is read into memory.
- `POST /api/topics` — req `TopicIntakeRequest` (`NewTopic` plus `sourceIds` and `pastedMaterial`), ok `ApiOk<Topic>`, err `ApiErr` (`validation` | `conflict`). Creates the topic in `queued`, then moves any staged material into it; does **not** dispatch. `DELETE /api/topics/:id` removes the topic's `source/` directory along with it.
- `GET /api/topics` — ok `ApiOk<DashboardView>`, err `ApiErr`.
- `GET /api/topics/:id` — ok `ApiOk<{ topic: Topic | DegradedTopic, graph: ModuleGraph, availability: ModuleAvailability[] }>`, err `ApiErr` (`not-found`).
- `DELETE /api/topics/:id` — ok `ApiOk<{ deleted: true }>`, err `ApiErr`. Works on a degraded topic.
- `GET /api/topics/:id/stream` — SSE of `GenerationProgress`; ok `text/event-stream`, err `ApiErr`.
- `POST /api/topics/:id/generate` — ok `ApiOk<Job>`, err `ApiErr` (`not-found` | `conflict`). The press is the authorisation; there is no token to mint or redeem.
- `POST /api/topics/:id/retry-module` — req `{ moduleId: ModuleId }`, ok `ApiOk<Job>`, err `ApiErr`.

- `POST /api/modules/:id/ask` — req `{ question: string }`, ok `ApiOk<LessonQuestion>`, err `ApiErr` (`validation` | `not-found` | `cli-failed` | `timeout`). Waits on one model turn; ungraded and unrelated to `/api/eval`.

**Shape contracts (owned by C9):**

**Depends on:** C0, C1, C2, C4, C5, C6, C7, C8, C11
**Consumes shapes:** every request/response shape named above, all from C0 or the owning component

**Release surface:** production
**Excluded from release by:** n/a. There is **no** debug or test route: the fake CLI transport is selected inside C2 by an exact-value env comparison in a `IS_RELEASE`-excluded module, not by an HTTP endpoint.

**Failure & recovery:**
- missing or wrong bearer token → `401` with `{ code: "unauthorized" }` and no detail → the request never reaches a service → user exit: reload the page (the token is re-injected); if the token file is unreadable the startup screen says so
- request body fails shape validation → `400` with a field-level message and no echo of the submitted value → nothing is written → user exit: correct the input; the form keeps what was typed

- schema versioning: n/a
- recovery: unreadable/absent at read time → mint a new one and log loudly; the page reload picks it up

**Data & egress:**
- data classes held: `pii` in transit
- HTTP responses on `127.0.0.1:31544` ← `pii`, `internal` ← per-launch bearer token + origin check ← on

**Trust boundaries:**
- inbound: `http://127.0.0.1:31544/api/*` ← **any local process, and any page the learner has open in a browser** ← per-launch bearer token in `X-LA-Token`, plus an explicit `Origin` allowlist; unauthenticated requests are rejected before routing ← single-user, no roles

**Sinks:**
- fs-path at `/api/topics/:id` and `/api/modules/:id` ← `:id` from the URL ← validated against the `TopicId`/`ModuleId` pattern **in the route schema** before any service call; the resolved path is asserted contained by C0's `moduleDir()`
- template at every rendered response ← service data ← JSON only; no HTML is templated server-side from learner or model text

**Long-running work:**

**Concurrency model:** async event loop
**Offloaded to a thread/process:** nothing new — every handler awaits a service; the store's synchronous statements are bounded < 5ms at declared scale, asserted by the loop-blocking test on each route
**Shared locks held:** none of its own

**Design notes:** no UI. Route handlers are one file per resource, each ≤ 80 lines.

## C10: Web UI

**Summary.** Every browser surface: the dashboard, the topic graph view, the lesson viewer, the
Socratic chat, the review queue, the practice runner, the reflection journal, the prediction prompt,
the capstone workspace, the settings screen, and the recovery screens. React
components in the Next.js App Router, styled with Tailwind, dark-mode first, compact density.

**Implements:** F1, F3, F4, F5, F7, F8, F9, F10, F11, F12, F13 (their user-visible halves)

**Responsibilities:**
- Render the module **graph**, not a list: completed / available / not-yet-recommended, with ≥2
  available modules presented as an open choice and no implicit "next" that hides alternatives.
- Gate the explanation behind the warm-up: the explanation does not render until the learner
  attempts or explicitly skips the warm-up (F3 AC).
- Show learning goals before the explanation, always.
- Render an unmet-prerequisite advisory that takes exactly **one** acknowledgment click and then
  proceeds — never a hard lock.
- Render `Explanation.kind === "video"` as a link/embed opening in a new tab with
  `rel="noopener noreferrer"`; render `kind === "text"` as sanitized Markdown with HTML disabled.
- **Typeset LaTeX** on every learner-facing surface (F3). Math is split out of the source *before*
  the Markdown pass — so a formula's own backslashes and braces are never mangled as emphasis — and
  typeset with KaTeX; everything around it is escaped as before. Applies equally to the plain-string
  fields (learning goals, warm-up prompt, table headers/cells, captions, chat turns, practice stems),
  which reach the page through `MathText` rather than as raw text nodes. Fenced code, backtick spans,
  `\$`, and an unpaired `$` are all left as literal text, so "it costs $5" is a price and not a
  broken formula. KaTeX runs with `trust: false` and bounded `maxExpand`/`maxSize`, and invalid LaTeX
  degrades to the offending source in the error colour rather than failing the page.
- Render the **lesson body** (`ModuleContent.blocks`) as an interleaved sequence rather than one
  slab of prose: `prose` through the same sanitized-Markdown path as the explanation, `figure`
  through the SVG sanitizer, `table` as a real table, and the three interactive kinds — `check`
  (one question, immediate feedback, re-pickable because nothing is recorded), `reveal` (answer
  withheld until asked for), `steps` (one step at a time, clamped at both ends) — as local

  lessons authored before the field existed still render, and `blocks` is optional *without a
  default* precisely so C4's content digest over already-stored lessons still matches.
- Omit the visualization section entirely when `kind === "none"` — no blank placeholder.
- Show progress with **no numeric or letter grade** anywhere.
- Offer the **source-material half of intake** on `/topics/new`: a file picker (multiple, PDF/DOCX/
  text/Markdown) and a paste box, both optional, both skippable, neither blocking submit when
  empty — a learner who uploads nothing follows the exact path they followed before. What comes
  back is shown to them while they are still on the form: the units we read, the pages, the
  characters, and the subject we inferred. A read in flight holds the submit button and only that,
  because submitting through it would file the topic under whatever was in the field a moment ago.
- Treat an inferred subject as a **pre-fill and never a decision**: it fills the field while the
  field is empty or still holds a previous inference, and the moment the learner types in it the
  text is theirs — no later upload overwrites it. The form says where the pre-fill came from.
- Say the three things the material can be wrong about, once each and without enforcing any of
  them: it is longer than one course and we kept part of it; it names no units so the order will be
  ours; it reads as a different level than the one chosen — and in that last case the lessons stay
  at the learner's answer, because a book is evidence about the book.
- Surface an extraction refusal **next to the paste box that is the way around it**, keeping
  everything else the learner has typed, and leave the picker clearable so the same file can be
  chosen again after a failure.
- Implement every qualifying interaction optimistically (below).
- Distinguish empty from failed in every list: "nothing here yet" and "couldn't load this" are
  different components and never substitute for one another (H3).
- Render the one machine-level banner that is left: the Claude CLI is missing. It says nothing
  while the helper is present and nothing before the answer arrives — a claim about the machine is
  never made from an unloaded store (H3).

**Optimistic operations** (each `await`s a round-trip on an interaction path, so each is optimistic
per SKILL.md § "Optimistic UI" — apply locally on the same tick, persist in the background, reconcile
or roll back on settle, and never disable the control for the round-trip):
- send an evaluation/synthesis/capstone chat message (F4/F9/F13) — the message appears and the composer clears and stays enabled immediately
- mark a module complete and flip newly-available modules in the graph (F4/F5) — reconciled against the evaluator's verdict
- record or skip a prediction (F10)
- save or edit a reflection (F11)
- answer or skip a practice question (F8) and record a review outcome (F7)
- acknowledge a prerequisite advisory and enter the module (F3)
- attempt or skip the warm-up (F3)

## C11: Source material (extraction, storage, and the views F2 reads)

**Summary.** Everything that happens to material the learner brought: reading text out of an
upload **in this process**, working out what the material says about itself, keeping the text and
the original on disk beside the topic's module directories, and deriving the bounded views the
orchestrator's sessions read. It is the only component that parses a document format, and it
reaches no network at all.

**Implements:** F1 (the source-material intake path), F2 (material as evidence constraining the graph)

**Responsibilities:**
- Decide what a file **is** from its bytes first and its name second, and dispatch to the reader for
  that format: PDF via `pdfjs-dist`'s legacy build in-process, DOCX by inflating the one member of
  the zip that matters with Node's own `zlib`, text and Markdown by decoding. **No OCR, no remote
  parsing service, no network call on any path.**
- Return usable text or the **specific reason there is none** — never an empty extraction dressed up
  as a success. A PDF that yields no text is reported as a *scan*, distinctly from a file that is
  damaged, and every refusal message names the paste box that is the way around it.
- Normalize once for everything downstream: one newline convention, page breaks kept as `\f`,
  mid-word hyphenation across a line break rejoined, word-processor invisibles removed.
- Read what the material declares about itself **with rules, not with a model** — units, key terms,
  subject, level signal. This runs while the learner waits on the intake form and before a provider
  is necessarily configured, so it must be free, offline and deterministic.
- Hold an upload in **staging** between "read this" and "this is the subject it belongs to", and
  sweep staging on a TTL — it is the one place a file lives with no topic to own it.
- Write the extracted text **and the original upload** under `<dataRoot>/topics/<topicId>/source/`
  with the same temp → fsync → rename protocol and the same path confinement the module
  directories get.
- Chunk long material and derive the two bounded views (`researchView`, `moduleView`), each
  reporting what it omitted so the reading session is told it holds an extract.

**Interfaces (public surface):**
- `extractSource(bytes: Uint8Array, filename: string, mimeType: string | null) -> Promise<ExtractionOutcome>` — the one door every upload comes through.
- `extractPastedSource(text: string) -> ExtractionOutcome`
- `extractUnits(text) -> SourceUnit[]`, `inferSubject(text) -> string | null`, `detectLevelSignal(text) -> Level | null`, `keyTerms(text, units) -> string[]`
- `stageSource / readStaged / discardStaged / sweepStaging(dataRoot, ttlMs, now) -> number`
- `writeSourceDocument(dataRoot, topicId, record, text, original) -> void`, `readSourceText(dataRoot, topicId, sourceId) -> string | null`
- `chunkDocument(text, label) -> SourceChunk[]`, `scopeDigest(units, chunks, budget) -> BoundedView`, `selectExcerpts(chunks, query, budget) -> BoundedView`
- `loadMaterial(store, dataRoot, topicId) -> TopicMaterial | null` (memoized per topic), `researchView(material) -> MaterialBrief`, `moduleView(material, query) -> MaterialBrief`, `resetMaterialCache()`

**Shape contracts (owned by C11):**
- `ExtractionOutcome` = `{ ok: true, kind: SourceKind, text: string, pageCount: number | null, truncated: boolean } | { ok: false, reason: "unsupported" | "too-large" | "unparseable" | "no-text" | "empty", message: string }`
  - example: `{ "ok": false, "reason": "no-text", "message": "That PDF is a picture of a page, not text — a scan. …" }`
- `SourceChunk` = `{ label: string, text: string, ordinal: number }`
  - example: `{ "label": "syllabus.pdf · Unit 3: Entropy", "text": "Entropy of a discrete source…", "ordinal": 4 }`
- `BoundedView` = `{ blocks: { label: string, text: string }[], omitted: number }`
  - example: `{ "blocks": [{ "label": "The units this material names, in its own order", "text": "Unit 1: Probability review\nUnit 2: Entropy" }], "omitted": 3 }`
- `TopicMaterial` = `{ documentCount: number, units: SourceUnit[], keyTerms: string[], chunks: SourceChunk[], truncated: boolean }`
- `MaterialBrief` = `{ units: SourceUnit[], keyTerms: string[], blocks: { label, text }[], omitted: number, truncated: boolean, documentCount: number }` — the only shape that ever enters a prompt.

`SourceId`, `SourceKind`, `SourceUnit`, `SourceDocument` and `StagedSource` live in C0's registry
with every other cross-component shape.

**Depends on:** C0 (paths, ids, errors, logger), C1 (`sources` repo — the index of what exists)
**Consumes shapes:** `SourceId`, `SourceKind`, `SourceUnit`, `SourceDocument`, `StagedSource`, `Level`, `TopicId` (C0)

**Chunking strategy (the decision, recorded here rather than left implicit).** A learner may bring a
600-page textbook, and no session's context holds one. Truncation was rejected outright: the first
20,000 characters of a textbook are its table of contents and its marking policy — the least useful
slice there is. Instead the document is cut **structurally first** — on the headings the material
itself uses, which is the same boundary set that names the units — and then on paragraph breaks,
to a 4,000-character chunk. Two views are then derived, each shaped for the session that reads it:

| View | Reader | What it contains | Budget |
|---|---|---|---|
| scope digest | the research session (one per topic) | every unit heading in the material's own order, plus the opening ~240 characters under each | 12,000 chars |
| module excerpts | each authoring session (one per lesson) | the chunks scoring highest against that module's title and objectives, returned in **document order**, each labelled with its section | 6,000 chars |

Scoring is token overlap with a heading hit worth five times a body hit, because a hit in a heading
is what a section is *about*. A module that matches nothing — typically a prerequisite the app added
because the syllabus assumed it — falls back to the opening chunks rather than to no material at
all. **Both views carry an `omitted` count into the prompt**, so a session always knows it is
reading an extract; nothing is ever trimmed in silence.

**Release surface:** production
**Excluded from release by:** n/a. `src/source/pdf.testing.ts` builds fixture PDFs for the tests and
is imported by tests only.

**Failure & recovery:**
- file is not a format we read (a spreadsheet, an image, a `.doc`) → `validation` with the `unsupported` message, which names the paste box → nothing is staged and the form keeps everything else typed → user exit: paste the text, or export to a format we read
- file is damaged, password-protected, or not the format its name claims → `unparseable`, with the cause logged and **not** returned → nothing staged → user exit: export it again, or paste the text
- PDF has no text layer (a pure scan) → `no-text`, whose message says it is a scan and that we do not run OCR → nothing staged; **no topic is created from it** → user exit: the paste box, or a copy with selectable text
- upload exceeds 25 MB → `too-large`, refused on the declared size **before** the body is read into memory → nothing read → user exit: upload the chapters needed, or paste
- a PDF runs past `MAX_SOURCE_PAGES` pages, or its text fills the 2,000,000-character budget as the pages accumulate → the read stops there and `truncated: true` travels with what was kept → the reading itself is bounded, not just what is stored, so a 3,000-page document never costs 3,000 page parses → user exit: upload the chapters actually needed
- extracted text exceeds the 2,000,000-character cap → the text is kept to the cap and `truncated: true` travels with it all the way to the intake form and into every prompt → the course still generates, from the part that was kept → user exit: upload the chapters actually needed
- a staged upload is claimed by no topic → swept after 24h by the next stage call → the learner's 25 MB does not sit forever in a directory no screen shows them → user exit: n/a
- a staged id is gone at attach time (swept, or never written) → that document is skipped and logged; the topic keeps the material that survived → the topic already exists by then, and failing would leave the learner with a subject and no retry → user exit: the course runs on what attached, exactly as if less had been uploaded
- the index names a document the disk does not have → `loadMaterial` drops it and logs; the course runs on the readable documents → a partial constraint beats refusing to generate → user exit: n/a
- a source row will not parse → dropped and logged (C1) → the topic researches from subject and level, which is the no-material path → user exit: n/a

**State lifecycle:**
- location: `<dataRoot>/topics/<topicId>/source/<sourceId>.txt` (extracted text) and `<sourceId>-<safe filename>` (the original upload); `<dataRoot>/staging/<sourceId>/` while an upload waits for a topic
- key custody: n/a — no key, no secret
- durability: temp → fsync → rename → fsync dir, the same protocol `content.json` is written with
- file mode: 0600 on files, 0700 on directories, set on the temp file before the rename (no-op on Windows)
- schema versioning: the on-disk text is plain UTF-8 and needs none; the index is `source_documents`, added by C1 migration **v4**
- recovery: text unreadable → treated as a missing document (above), never as a corrupt topic | staged meta unparseable → the staged record reads as absent | the whole `source/` directory removed with the topic

**Data & egress:**
- data classes held: `pii` — the material is the learner's own book and their own syllabus, and it is the largest piece of learner data the app holds
- topic source directory (`<dataRoot>/topics/**/source/`) ← `pii` ← path confinement via C0's `sourceDir()`, asserted before a byte is written ← on
- staging directory (`<dataRoot>/staging/`) ← `pii` ← `SourceId` pattern checked, join resolved, containment asserted; swept on a 24h TTL ← on
- provider session (prompt body, via C2) ← `pii`: unit titles, key terms and bounded excerpts of the material — **never** the file, never the whole document ← the same gate as every other prompt: the learner's press on the named control ← on
- log sink ← `internal` only: `sourceId` (a minted opaque id, exempt in `scrub()` exactly as `topicId` is), kind, counts. Filenames, unit titles and extracted text are **not** exempt and are hashed like every other piece of learner writing ← `scrub()` ← on
- **no network destination of its own.** Extraction opens no socket on any path.

**Trust boundaries:**
- inbound: the uploaded bytes ← the learner, through `POST /api/source` (C9) ← the format is decided by magic number before any reader runs, the size is refused on the declared length first and the real length second, and the parse runs with no filesystem or network access of its own ← the file is untrusted input to a parser, which is the sharpest edge in this feature
- inbound: extracted text on its way into a prompt ← the learner's own document ← rendered into the prompt inside a fenced, explicitly-labelled untrusted-data block by C2's `materialBlock()`, so a syllabus that says "ignore your instructions" is quoted material and not an instruction
**Sinks:**
- fs-path at `stagedDir()` ← `SourceId` from the request ← matched against `SOURCE_ID_RE` before the join, resolved, and asserted contained by the staging root
- fs-path at `writeSourceDocument`/`readSourceText` ← `TopicId` + `SourceId` ← both matched against their patterns, resolved, and asserted contained by the topic's `source/` directory (H12: a shape guarantees structure, never a location)
- fs-path at the kept original ← the learner's own filename ← `safeFilename()` strips a path, a drive letter and anything not plainly part of a name, so the join stays one segment
- url: none

**Long-running work:**
- reading one upload | max: bounded by the 25 MB cap, by `MAX_SOURCE_PAGES` pages, and by `MAX_SOURCE_CHARS` characters counted as the pages accumulate | timeout: none of its own; the request's | cancellable: with the request | owner: the HTTP request | on owner exit: the parse is abandoned and nothing is staged | progress: the form says it is reading, on this computer
- chunking a topic's material | max: bounded by the 2,000,000-character cap × 10 documents | done once per topic per process and memoized, because one authoring pass writes a whole window of lessons that all want an excerpt from the same book

**Concurrency model:** async for the PDF read (it awaits `pdfjs` once per page) and for normalizing an extracted upload; sync for everything else
**Offloaded to a thread/process:** none, and no worker thread exists anywhere in this app — `pdfjs`'s legacy build runs on the event loop. Three ceilings bound it instead of a thread: 25 MB of file, `MAX_SOURCE_PAGES` pages, and `MAX_SOURCE_CHARS` characters counted as the pages accumulate, so a 3,000-page book costs the pages it took to fill the budget rather than the whole book. Crossing any of them sets `truncated`, which the intake form turns into a note naming the file. Normalization is the one genuinely uninterruptible stretch, so `normalizeSourceTextAsync` folds the text line by line and yields the loop every 64 KB: the same process serves the UI and the SSE generation stream, and one unbroken pass over 2M characters is a freeze rather than a slowdown
**Shared locks held:** none. `loadMaterial`'s memo is a bounded per-process map, cleared by `resetMaterialCache()` in tests.

**Design notes:** the intake surface belongs to C10 (`SourceMaterial.tsx`); this component renders
nothing. Every refusal message it owns names the paste box, because a dead end without a door out
of it is the failure this whole path exists to remove.

**Files:**

## Hardening summary (architect-gate review)

**Features that spend (6):** F1, F4, F7, F9, F12, F13. This is a single-user, locally hosted app run
by its own author, so the control the learner presses IS the authorisation: nothing asks a second
time, and there is no gate object to fail open. **C2** is the only component that spawns a session —
`tests/cli/only-spawner.test.ts` asserts it — so there is still exactly one path from intent to
subprocess, and the one limit on that path (`sessionConcurrency`) is a queue about provider load,
never a refusal.

**Egress destinations (16), of which off-machine and on by default: 1.** That one is the `claude`
CLI subprocess and, through it, the Anthropic API. It carries `pii` — the learner's own words, and
now bounded excerpts of the material they uploaded — and it is **on**, because a learning app that
cannot call the model does nothing. Every other hosted provider row defaults **off** and only opens
when the learner selects that provider; the local-model rows do not leave the machine at all. No row
returns a `secret`; the app holds no credential of its own. The outbound video link is a URL the
learner clicks, with `no-referrer` and `noopener`. **Extraction itself has no network destination**:
a learner's textbook is read in this process and stored on this disk, and the only part of it that
can ever leave is the excerpt a session is given.

**Components owning persistent state (5):** C0 (`.scrub-salt`), C1 (`learn.db` + one prior
generation), C4 (module directories, with the row written second so an interruption never yields a
silently-skipped module), C9 (`.session-token`), C11 (each topic's `source/` directory and the
staging directory, both written with C1's durability protocol and both swept or deleted with what
owns them).

**Inbound surfaces (1):** `127.0.0.1:31544`. It is authenticated by a **per-launch bearer token**
plus an explicit origin allowlist — loopback is explicitly *not* treated as authentication (H12).

**Sinks declared:** fs-path (C0, C2, C4, C9), exec (C2), url (C4, C10), deserialize (C2, C4, C6),
sql (C1), template (C6, C7, C9, C10). Every one names a confinement; every one has an abuse-test
battery planned.

**Trust note that shaped several decisions:** the Claude CLI's output is **untrusted input**. It is
model-generated content that becomes module explanations, SVG visualizations, video URLs, and
evaluator verdicts. It is schema-validated at ingest (C4), sanitized at render (C10), host-allowlisted
for URLs at both ends, and a `pass` verdict is cross-checked against the module's `passCriteria`
before it can grant completion.

⚠ **Review the egress matrix in § C0 before approving.** That table is where the expensive mistakes
live, and the single row that matters here is the `claude` subprocess: it is the only way the
learner's text leaves the machine, and every path to it goes through C2.
