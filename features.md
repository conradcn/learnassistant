# Features

*This is the generated specification of the system — the intent the code is built and kept in sync
against. It is a reference document, not a guide: for an introduction start at
[`README.md`](README.md), and to work on the project read [`CONTRIBUTING.md`](CONTRIBUTING.md).
The quotation below is the originating request the spec was generated from.*

> `fractal init` 2026-08-22 — req: "A tool that takes a subject and level, researches to find a sufficient curriculum, and uses recursive subagents to develop lessons with learning goals and, where applicable, visualizations. Lessons should be structured in 20 minute chunks when possible, but flexibility is fine when merited. If there is a well regarded explanation on a topic on a video hosting site that would be comprehensible, link to it. Otherwise, generate an explanation that is appropriate for the user's current level of understanding. These should be as terse as possible while still remaining usable. At the end of each section is an evaluation structured as a chat. Evaluations should be narrative and Socratic where applicable. Exercises should require the user to fully specify a solution to a problem. The goal is to know the material well enough to thoroughly understand wikis and papers, sharpen one's understanding of the world, and use it to build in collaboration with AI agents. There's no need to memorize exact formulas or computation that would be abstracted out in practice. Once the evaluator agent is satisfied that the user understands the material, the section is marked as completed. An evaluation failure should begin a discussion explaining the misunderstanding and re-evaluation until passing. Reevaluation should ask the question from a different angle if possible to avoid simple memorization. Mechanically, this is a self-hosted website to track learning. When the user adds a new topic, it runs a dedicated Claude code skill to generate the lesson plan using sub agents to research and compose each module. When completed, a final check reviews for discontinuity. Runtime AI work should use the Claude CLI, with one session per module. The sessions should be scoped such that they can only read and modify the module files, but don't get bogged down with excessive tools or the full codebase. Follow progressive education principles when possible. Deviate only when they would violate the spirit of the exercise."

## F1: Topic intake

- Form: subject (free text) + level (beginner/intermediate/advanced or self-described background) + purpose (free text: why learn this / what the learner wants to build or understand with it — Dewey: curriculum connects to learner purposes)
- Optional short diagnostic chat before generation: elicits what the learner already knows about the subject (Ausubel: build on actual prior knowledge, not a level label); skippable; transcript passed to F2 so likely-known material is marked `test-out-eligible` rather than re-taught
- **Second intake path — the material the learner already has.** A learner with an assigned textbook, a course syllabus or a set of lecture slides can hand it over instead of describing the subject and hoping the research lands on the same course: upload one or more files (PDF, Word `.docx`, plain text, Markdown) or paste a syllabus straight into the form. Both paths are first-class — material **supplements** the intake and never replaces it, subject/level/purpose stay exactly where they are, and a learner who uploads nothing follows precisely the path they followed before, with no source directory and no source rows written
- Extraction runs **locally, in this process**: the PDF text layer is parsed in-process, no file is sent to a remote service, and there is no OCR dependency. It costs nothing and needs no configured provider, so it happens while the learner is still on the form and they can see what we read before a single session is dispatched
- What the material says about itself is read with **rules, not a model**: the units/weeks/chapters it names in the order it names them, the terms it uses for its own ideas, the subject in its title, and the level it reads as. The subject **pre-fills** the field and the learner can overwrite it — once they have typed in it, it is theirs and no later upload overwrites it. The level the material reads as is only ever shown when it disagrees with the level chosen; the lessons are pitched at the learner's answer, because a book is evidence about the book
- Material is learner data (`pii`): extracted text **and** the original upload are stored under `<dataRoot>/topics/<topic>/source/` beside the module directories, under the same C2 path confinement, indexed one row per document, covered by `scrub()`, and removed with the topic
- Kicks off curriculum generation job; user sees pending state, not blocked
- AC: submit creates a topic record in `queued` state; AC: duplicate subject+level warns before resubmitting; AC: form disabled fields re-enable instantly on submit (optimistic), job status polled/streamed separately; AC: purpose and diagnostic transcript (if any) are stored on the topic record and readable by F2; AC: skipping the diagnostic proceeds straight to generation with no penalty or nag
- AC: submitting with no material creates the topic on the existing path — no source directory, no source rows, no change to what F2 does; AC: a topic created with material stores the extracted text and the original upload under that topic's `source/` directory and one `SourceDocument` row per piece of material, and both are removed when the topic is deleted; AC: material whose title names a subject pre-fills the subject field, and text the learner typed into that field survives any later upload; AC: extraction never opens a network connection and never invokes a provider; AC: a PDF with no extractable text is refused with a message that says it is a scan and names the paste box, and no topic is created from it; AC: a path that would resolve outside `<dataRoot>/topics/` is refused before any byte is written
- paths: happy (valid subject+level+purpose) / empty subject rejected / resubmission of a topic already `ready` / diagnostic skipped / diagnostic reveals substantial prior knowledge (affected modules flagged `test-out-eligible`) / material uploaded or pasted (subject pre-filled from it, units listed back, F2 given it as evidence) / unparseable file — damaged, password-protected, or not the format its name claims (refused by name, the paste path offered, and everything else typed into the form kept) / scanned PDF with no text layer (refused *as a scan* specifically — we do not OCR and say so — with the paste path offered) / material far larger than one course (kept to the cap, the learner is told what was left out rather than it being trimmed in silence, and lessons are written from the sections that match them) / material that contradicts the stated level (both kept: lessons stay at the level the learner chose and the disagreement is said once, not enforced)
- perf: submit <100ms p95 (UI ack only, not job completion); extraction of a 50-page PDF <5s p95, local and in-process — it holds the intake button, nothing else
- scale: topics=50, modules per topic=12, diagnostic exchanges=5, source documents per topic=10, upload=25 MB per file, extracted text kept=2,000,000 characters per document
- e2e: yes

## F2: Curriculum research & generation

- Orchestrator: given subject+level+purpose (and F1 diagnostic transcript if any), researches a sufficient curriculum before authoring content: a driving question anchoring the whole topic (project-based-learning research: an anchoring question holds atomized modules together), plus a module graph — a DAG of modules with prerequisite edges — rather than a linear sequence
- Graph shape: prerequisite edges only where understanding genuinely depends on the other module; prefer wide/shallow graphs over chains so several modules are typically available at once and the learner chooses by interest; a strictly linear subject may still produce a chain (graph "when possible", not forced)
- **Material the learner brought (F1) constrains the graph — as evidence, not as gospel.** The orchestrator still researches and still builds a prerequisite DAG; the syllabus's stated scope, sequence and terminology bound what that graph covers. Where the material names a unit, lessons cover it: every named unit is checked against the outline that comes back, and one that nothing reaches is inserted rather than reported (the plan floor reserves the room for it, so a syllabus's units cannot be squeezed out by the count). Where the material is silent on a prerequisite the learner plainly needs, the prerequisite is still added — a syllabus states what a course covers, not everything a reader must already know. Where the two disagree on a fact, research wins; where they disagree on a *name* for the same idea, the material wins, because that is the word the learner will meet in their own book and their own exam
- Long material is never truncated in silence. It is chunked on its own headings and then paragraphs, and two **bounded views** are derived, each built for the session that reads it: research gets a *scope digest* — every unit heading in order, each with its opening lines, to a fixed budget — because scope and sequence is what an outline pass needs; each authoring session gets the *excerpts* that match its own module's title and objectives, in document order, labelled with the section they came from. Both report how much they left out, and the report goes into the prompt, so a session always knows it is reading an extract of a longer document
- Learner purpose threads through authoring: examples, exercise framing, and the capstone spec (F13) are chosen to serve the stated purpose where the subject allows
- Recursive subagents: one dedicated Claude CLI session per module, sandboxed to read/write only that module's files (module dir), no full-codebase or excess tool access
- Each module targeted at ~20-minute chunks; split or merge when the topic doesn't decompose cleanly (flexibility over rigid chunking)
- Each module authored with: learning goals, a short warm-up problem to attempt before the explanation (productive-failure sequencing — Kapur; Schwartz & Bransford), explanation (video link if a well-regarded comprehensible one exists, else terse generated text calibrated to stated level), visualization where applicable, Socratic evaluation script, and — only where the lesson contains flat facts nothing derives — a small pack of flash cards (F14) offered to the learner rather than added for them
- Modules covering material the F1 diagnostic showed the learner likely already knows are marked `test-out-eligible`
- Dedicated capstone-spec session authors the F13 capstone project spec from the driving question and learner purpose, with its own prerequisite edges into the module graph
- Final pass: dedicated discontinuity-review session reads all modules for the topic (goals/prereqs/terminology consistency across module boundaries); also validates the graph: acyclic, at least one entry module (no prereqs), no module unreachable from the entry set, prereq edges consistent with module content
- What the check finds is FIXED, not reported: each finding is routed back to the lesson it names (by the ids the reviewer gave, else by the lesson numbers and titles in its prose), those lessons are rewritten with the finding attached, and the check runs again over the result — up to a bounded number of fix-and-recheck rounds. A learner cannot act on "no lesson owns the Hessian"; the writer can. Anything still standing when the rounds run out goes to the log, not to the topic page — as does every graph defect, which validation has already corrected before anyone could see it
- One lesson is one idea in one sitting (~20 minutes), and a broader subject buys MORE lessons rather than wider ones — the plan has a floor but no ceiling, because "high school biology to MCAT-ready" is a legitimate ask and capping the count only made each lesson span several topics
- Lessons are prepared a window at a time, not a plan at a time: each pass writes the lessons the learner can start now, then the unwritten lessons nearest behind them in the prerequisite graph (a bounded lookahead, capped in count), and the topic page then offers the next pass. A subject holding a lesson the learner has unlocked but nobody has written is picked up by a background sweep — including one left in `needs-attention` by a single failed session, which is retried a bounded number of times before it is left to the learner. Pressing the control is the authorisation; nothing asks a second time. The whole plan is visible from the first pass; only the writing is paced
- Lessons the learner has just unlocked are prepared in the background: passing a lesson whose prerequisites were the last thing standing in front of the next ones starts the writing pass for them there and then, exactly as pressing the button would. A learner who follows "this opened up" into the next lesson finds it written rather than empty
- When the user has other completed/in-progress topics, discontinuity review also checks for missed cross-topic connections (terminology overlap, prerequisite relationships between topics) and surfaces them as candidate F9 synthesis prompts rather than silently ignoring them
- AC: every module has learning goals, a warm-up problem, an explanation (link xor generated text), and an evaluation before topic flips to `ready`; AC: the module graph is acyclic with ≥1 entry module, and stores explicit prerequisite edges (not an implied linear order); AC: a capstone spec referencing the driving question exists before topic flips to `ready`; AC: discontinuity review runs exactly once per set of lessons, on the pass that finishes the course, and its findings are resolved by rewriting the lessons they name rather than shown to the learner; AC: a module session cannot read/write files outside its own module directory; AC: when the learner brought material, every unit it names is covered by at least one module in the generated graph, and the modules the material does not name are still added where the subject requires them; AC: no session is handed more of the material than its budget allows, and any session reading an extract is told so in its own prompt
- paths: happy (curriculum generates end-to-end as a branching graph) / subject decomposes strictly linearly (chain produced, no artificial branches) / research finds no suitable outline (falls back to generic decomposition by subtopic) / a module session fails or times out (topic marked `needs-attention`, partial modules kept, retry offered, and the background sweep retries the pass a bounded number of times rather than leaving the subject parked) / discontinuity review finds a gap (the lessons it names are rewritten and the check re-run; topic flips to `ready` when the loop converges, and the residue is logged when it does not) / a finding names no lesson this topic has (nothing to rewrite, so no further check is paid for) / graph defect (the edge is dropped or the island opened, and the correction is logged rather than noted) / a course longer than one prep window (the whole plan is stored, the first window is written, and the rest waits for the next authorised pass) / the outline comes back missing a unit the material names (the unit is inserted into the plan in the material's own order, displacing filler rather than being dropped) / research finds no outline at all but material exists (the material's own units and order become the plan, rather than the generic subtopic fallback) / material longer than a session's context (chunked and viewed, never truncated in silence; the omission is stated in the prompt) / the index says a document exists and the disk does not (the course runs on the documents that are readable, and the missing one is logged)
- perf: full topic generation <20min p95 per prep pass (background; not UI-blocking)
- scale: modules per topic=unbounded (floor 6, or the number of units the material names up to 60, typically 10-30), material read per research session=12,000 characters (scope digest), per authoring session=6,000 characters (excerpts), chunk=4,000 characters, lessons prepared per pass=10, subagent sessions per topic=modules + 1 research + 1 capstone spec + 1 discontinuity review + a ceiling of 2 repair rounds of 3 lesson rewrites and 1 re-check
- e2e: yes

## F3: Lesson viewer

- Presents one module in sequence: learning goals, warm-up problem (one short attempt prompt before the explanation; ungraded, skippable), explanation (embedded/linked video or generated text), then the lesson body
- The body is interleaved, not a wall of text: an ordered sequence of blocks alternating prose with something to look at (SVG figure, table) or something to do (a one-question check with immediate feedback, a try-before-you-look reveal, an interactive plot the learner drives with sliders — up to three curves given as formulas in `x` and the slider names, redrawn as the learner drags — or, for what a curve cannot express (a simulation, a draggable construction, an animated algorithm, a random experiment), a visualization the lesson writes as HTML and JavaScript and that runs as written in a sandboxed frame); the authoring contract caps prose at two consecutive blocks, requires at least one look-at block and at least one do block per lesson, and asks for a plot rather than a static figure wherever the subject has a knob worth turning. A derivation is printed whole rather than walked one line at a time: clicking through "Next step" is tabbing, not thinking
- "Ask a question about this": from inside the lesson, the learner can ask their tutor about anything on the page and get an answer bounded by what this lesson taught — a hand raised mid-lesson, not the F4 evaluation. Ungraded, it opens no evaluation and moves no progress; the exchanges are kept with the lesson so a revisit shows what was already asked
- Every in-lesson interactive is ungraded and unrecorded: it makes the learner commit before reading on, and nothing it does gates the rest of the lesson — being right or wrong has consequences only in F4
- Topic navigation is a module-graph view, not a list: modules shown as completed / available (all prereqs met) / not-yet-recommended (unmet prereqs); the learner picks whichever available module interests them most — no forced order among available modules
- Prerequisites are advisory, not hard locks (learner agency over gates): entering a module with unmet prereqs shows a warning naming the missing prereqs and requires one explicit acknowledgment, then proceeds
- Test-out: any module (highlighted when marked `test-out-eligible` by F2, but allowed for any) can jump straight to its F4 evaluation, skipping the lesson; passing marks it complete
- Math is typeset, not shown as source: the authoring session writes formulas as LaTeX and every learner-facing surface renders it — explanation, learning goals, warm-up prompt, visualization captions/tables, evaluation chat and practice questions
- AC: a lesson body renders its blocks in authored order, and its checks and reveals withhold their answer until the learner acts (no feedback before a pick, no answer before a reveal); AC: a plot redraws from its own formulas as a slider moves, can be put back where it started, describes itself for a learner who cannot see it, and is refused at authoring time if a curve names a slider that does not exist; AC: a lesson-written visualization runs its own script, and that script cannot read the page around it, the app's storage or session credential, or the network; AC: a lesson written without a body renders exactly as before, with no empty section and no checksum failure; AC: learning goals visible before explanation; AC: warm-up (unless skipped) is presented before the explanation renders, and the explanation is not shown until the learner attempts or skips it; AC: video link opens in new tab / embed, generated text renders as formatted content, and LaTeX renders as typeset math rather than literal backslashes; AC: whenever the graph allows ≥2 concurrently available modules, the viewer presents them as an open choice (no implicit "next" that hides alternatives); AC: entering a module with unmet prereqs requires exactly one acknowledgment click, never a hard block; AC: a question asked about the lesson is answered from that lesson's own content, is never graded, never opens or affects an F4 evaluation, and is shown again with its answer the next time the lesson is opened
- paths: happy (choose among ≥2 available modules) / enter a module past the unmet-prereq advisory / test out of a module directly into its evaluation / warm-up skipped / module has no visualization (section omitted, not a blank placeholder) / a lesson authored before the body existed (explanation only, body section absent) / a non-mathematical lesson mentioning a price keeps its dollar sign as text / a question asked mid-lesson (answered, remembered) / a question asked while the tutor is unreachable (the typed question is handed back, never lost)
- perf: module render <200ms p95; first-paint <1500ms p95
- scale: modules per topic=12, topics=50
- e2e: yes

## F4: Socratic evaluation chat

- End of each module (or entered cold via F3 test-out): chat-based evaluation, narrative/Socratic questioning, exercises require the user to fully specify a solution (not recall a formula); exercises framed in authentic contexts drawn from the learner's stated purpose (F1) where the material allows
- Evaluator (Claude CLI session scoped to the module's content + user's chat transcript) judges understanding, not rote recall
- Self-assessment before verdict: after each substantive answer, the learner is asked to briefly rate/critique their own answer before the evaluator responds (self-explanation effect; skippable, non-blocking); the pair feeds F10 calibration
- Graduated hints instead of binary pass/fail per exchange (scaffolding-with-fading — Wood, Bruner & Ross): a struggling answer gets escalating hints before being ruled a failure; the evaluator records an assist level per exchange, and a pass earned with heavy hints is persisted as `assisted-pass` so F7 schedules it for earlier review
- On failure: explains the specific misunderstanding, discusses, then re-asks from a different angle (not the same question) until passing
- Teach-back mode: as one of the "different angles" (preferred in the remedial loop — protégé effect, ICAP), the evaluator flips roles to a confused-student persona with a specific planted misconception; the learner must diagnose and correct it to pass that exchange
- On pass: module marked complete; dependent modules whose prereqs are now all met flip to available in the graph
- AC: every exchange is persisted (resumable across sessions); AC: a failed attempt always includes an explanation before the next question; AC: re-asked question after failure is not a verbatim repeat; AC: assist level is persisted per exchange and readable by F7's scheduler; AC: a teach-back exchange passes only if the learner identifies and corrects the planted misconception; AC: the self-assessment prompt never blocks the evaluator (skipping it changes nothing but the F10 comparison); AC: completion updates progress and dependent-module availability in the same action (optimistic in UI, reconciled on evaluator response); AC: while a conversation is open, a transcript whose last word is the learner's is a turn still owed — the learner's message is persisted before the evaluator is called, so an interrupted turn is resumed from the saved message when the conversation is next opened, and a retry of the same text finishes that turn rather than appending it twice
- Mastery-learning correction: N consecutive failures (default 3) on the same underlying concept triggers a scoped remedial mini-module (targeted re-explanation of that concept only) before any further re-ask attempts — never loop the same question indefinitely without new instructional input
- paths: happy (pass on first attempt, unassisted) / pass with heavy hints (marked `assisted-pass`) / fail then pass on re-ask / re-ask served as teach-back, learner corrects the misconception / repeated failures trigger remedial mini-module, then re-ask / test-out entry passes cold / test-out entry fails (routed into the normal lesson, not the remedial loop) / user abandons mid-chat and resumes later / evaluator turn is interrupted after the learner's message is saved (restart, closed tab, dropped connection), and reopening the conversation resumes the owed reply
- perf: chat message round-trip UI feedback <100ms p95 (send is optimistic; evaluator judgment latency unbounded/background)
- scale: exchanges per evaluation=20
- e2e: yes

## F5: Progress tracking

- Per-user, per-topic, per-module completion state over the module graph; dashboard of topics showing position in each graph (completed / available / remaining) plus the capstone state (F13)
- Drives F3's availability highlighting per prerequisite edges (advisory, not hard locks)
- Formative framing: progress is expressed as "where you are and what's open next," never as grades or score-like aggregates (no percentages-as-marks, no letter equivalents); `needs-review` is visible as a review cue, while `assisted-pass` is never surfaced to the learner at all — how much help a pass took only weights F7's review scheduling
- Topic states distinguish `modules-complete` (all modules passed) from `done` (capstone also passed)
- AC: dashboard reflects latest completion within one reload; AC: progress persists across restarts (durable store, not in-memory only); AC: no numeric or letter grade appears anywhere on the dashboard; AC: a topic with all modules passed but capstone open shows `modules-complete`, not `done`
- paths: happy (topic with mixed complete/available/remaining modules) / topic with zero progress / all modules complete, capstone open (`modules-complete`) / capstone passed (topic `done`)
- perf: dashboard load <300ms p95
- scale: topics=50, modules under tracking=600, review queue depth=200
- e2e: yes

## F6: Module authoring sandbox (provider-agnostic session scoping)

- Infrastructure feature: defines how each recursive subagent session is invoked (one session per module, on whichever provider is selected) and confined to read/write only within that module's directory
- No UI; backs F2
- AC: a module-authoring session's file access is restricted to its own module directory (verified, not just documented); AC: session receives just enough context (topic, driving question, level, learner purpose, prerequisite edges, graph-adjacent module summaries) without the full codebase or excess tools
- The session's model provider is a setting with eight choices: the `claude` CLI (default), a model served locally by Ollama or llama.cpp, or the Anthropic, OpenAI, Google Gemini or Mistral API dialled directly with your own key — plus one OpenAI-compatible choice with a base URL you set, which is how LM Studio, vLLM, OpenRouter, Groq, Together, DeepSeek and the rest of the long tail are reached. Every choice satisfies the same contract: streaming, a system prompt, a multi-turn conversation for evaluation, and the file-scoped authoring path.
- Only the CLI can edit files itself. For every other provider the app reads the module's files in, sends them as part of the prompt, and writes the answer back inside the same directory the CLI would have been confined to — so the sandbox is one mechanism, not one per provider, and a chat API with no tools at all is a complete substitute.
- A hosted provider's API key is read from the environment or `.env` and nowhere else: it is never written to the settings file, never stored in the database, and never logged. Each also accepts the vendor's own conventional variable, so a machine already set up for that vendor needs no second copy of the same secret.
- Lesson planning and chat can name different models on the chosen provider. Authoring runs ahead of the learner and is judged on quality; an evaluation turn has a person waiting on it and is usually better served by a smaller, faster model. A chat model is an override — empty means one model does both jobs.
- AC: with a chat model set, an evaluation turn dispatches to it while authoring still dispatches to the planning model, on one provider and without restarting the app; AC: clearing the chat model returns both roles to the planning model; AC: a chat model that is set but unreachable or not installed is reported by the Settings probe as not-ready, naming the chat role, rather than failing first mid-conversation
- AC: switching provider in Settings takes effect on the next session without restarting the app; AC: the provider is probed before it is relied on, and an unreachable Ollama server or an un-pulled model is reported with the command that fixes it; AC: with a provider that runs on this computer selected, Settings says the text stays here, and with any other it names the service the text is sent to
- AC: Settings offers a connection test that makes one cheap call to the selected provider and reports in plain language whether it worked; AC: a missing key is reported as the name of the variable to set, never as a network failure, and no request is sent; AC: Settings shows whether a key is present without ever showing the key
- AC: every provider is covered by unit tests against a fake server, in the default test run; tests that touch a real network live apart from it
- paths: happy (session writes within bounds) / session attempts to read/write outside its module dir (rejected) / session runs out of context budget (fails gracefully, module marked `needs-attention` per F2) / local provider selected but its server is not running (session fails as `cli-missing` with the repair instruction, nothing is sent anywhere) / hosted provider selected with no key set (session fails naming the variable to set, and nothing leaves the machine) / hosted provider rejects the key or the model id (session fails with what the service said, retryable)
- e2e: no

## F7: Spaced review

- On module completion (F4 pass), schedule spaced-repetition retrieval prompts at increasing intervals using questions drawn from the module's Socratic eval bank, reworded rather than repeated verbatim
- The interval algorithm is **FSRS-6** (the `ts-fsrs` implementation), not a hand-rolled SM-2 ease multiplier. Each module carries a memory state — stability, difficulty, repetition count, last-reviewed instant — and the next interval is derived from it at a request retention of 0.9. The research behind this choice, including what we deliberately declined to take from FSRS, is in [`docs/spaced-repetition.md`](docs/spaced-repetition.md)
- Our signal is an evaluator's judgement of understanding, not a flashcard self-grade, so it maps onto **three** FSRS grades and never onto `Easy`: a clean or lightly-hinted outcome is `Good`, a pass bought with heavy help (`assisted-pass`, assist level ≥2) is `Hard`, and a failed retrieval is `Again`. A module *completion* is an encoding event rather than a retrieval attempt, so no amount of help records it as a failure
- Scheduler weights F4's recorded assist level: an `assisted-pass` module starts on a shorter first interval than an unassisted pass, and — unlike the old one-off shorter first interval — the difference persists into later intervals, because the `Hard` grade also raises the item's difficulty
- Reviews surface as a queue on the dashboard (F5), independent of any specific topic's linear path; answering correctly pushes the interval out, missing pulls it back in and re-flags the module as `needs-review`. A miss is registered from either route: the queue card's "I had forgotten this", or a review taken through the F4 evaluator chat whose hint ladder runs out
- Missing something held for months does not send it back to a beginner's interval, and a module missed early is not penalised forever — FSRS's post-lapse stability and mean-reverting difficulty replace SM-2's reset-to-1-day and never-recovering ease
- The memory state is **internal**. Stability, difficulty and retrievability order the queue and nothing else; they never cross the API boundary and never reach the UI, per F5's rule that progress is never expressed as a grade. What the browser receives is a review cue: which lesson, when it is due, and whether it needs another look
- Scheduling is deterministic — no interval fuzz, no provider call — so a given review history always produces the same schedule and a test can pin it down exactly
- AC: a completed module is never permanently "done" — it re-enters the review queue per the schedule; AC: a review question is not a verbatim repeat of the original eval question; AC: missing a review does not block other learning (queue, not gate); AC: no stability, difficulty or retrievability value appears in any API response or anywhere in the UI; AC: an existing learner's review schedule survives the upgrade — stored intervals are carried into the new memory model, never reset
- paths: happy (review surfaces on schedule, answered correctly, interval extends) / review answered incorrectly (interval shortens, module flagged `needs-review`) / module untouched long enough to hit max interval (still resurfaces, never "graduates" out of scheduling entirely)
- scale: modules under active review=600, reviews/day at steady state=15
- e2e: yes

## F8: Interleaved practice

- Periodic practice sessions mix retrieval questions across multiple completed modules/topics (not blocked by single topic), pulled preferentially from F7's due queue plus a sampling of not-yet-due material
- AC: a single interleaved session never draws all questions from one module/topic when ≥2 topics have completed modules; AC: session length is bounded (user can stop after any question, progress on answered questions is kept)
- paths: happy (mixed session across ≥2 topics) / only one topic has completed modules (falls back to single-topic practice, no error) / user stops mid-session (partial results saved)
- perf: session start <300ms p95
- scale: candidate module pool=600, questions per session=15
- e2e: yes

## F9: Cross-topic synthesis prompts

- Occasional evaluation sessions ask the user to explicitly connect two completed topics (candidates surfaced by F2's cross-topic discontinuity check, or any two topics with completed modules if none flagged)
- Structured as a Socratic chat like F4, judged the same way (full-solution answer required, narrative failure explanation, re-ask from a different angle)
- AC: a synthesis prompt names both topics explicitly in the question; AC: passing/failing a synthesis prompt does not affect either topic's own completion state (it's additive, not gating)
- paths: happy (user articulates the connection) / user fails and gets explanation + re-ask / fewer than 2 topics completed (feature inactive, not shown)
- e2e: yes

## F10: Learner-set goals & self-assessment

- Before a module (F3), briefly ask the user to predict confidence/what they expect to learn; after evaluation (F4) passes, show predicted vs. actual outcome (calibration feedback)
- Also folds in F4's per-answer self-assessments: the post-pass calibration view compares the learner's self-ratings against the evaluator's judgments for that module (one compact comparison, same formative framing)
- AC: pre-module prediction is a single lightweight prompt, not a blocking form (skippable); AC: calibration comparison is shown once per module, immediately after evaluation passes, not buried in a later report; AC: self-assessment comparison appears only when the learner provided self-assessments (absence is silent, not an empty section)
- paths: happy (predict, then compare after pass) / user skips prediction (module proceeds normally, no comparison shown) / prediction wildly miscalibrated (comparison still shown plainly, no judgment framing) / self-assessments present (included in the comparison)
- perf: prediction prompt render <100ms p95
- scale: modules with predictions=600
- e2e: yes

## F12: Learner-directed pacing & branching

- Mid-topic, user can request a detour/deeper-dive sub-module not in the original generated plan; treated as a request to extend the curriculum (routes to F2's orchestrator for a scoped, single-module addition) rather than a fixed immutable plan
- **A whole subject can be extended to a further goal.** A course the learner already has — "Practical Biology" — is carried to somewhere they now want to get to — "sufficient knowledge for the MCAT" — stated in their own words, as F1 asks for a purpose. It is one research pass over the course as it stands: what the extension plans is what is MISSING for the goal, so lessons already in the course are neither re-taught nor restated under a new name, and how many lessons it buys is read off the breadth of the goal by the same measure F2 sizes a plan by (with a ceiling, unlike a plan: an extension is an addition to a curriculum, not a second curriculum stapled to it)
- The extension is planning, not writing. It ends where research ends — the new lessons named and unwritten in the plan, and F2's prep-window control beneath them saying how many the next press writes. The learner authorised working out what is missing; a course's worth of writing sessions is a separate press
- New lessons hang off the ENDS of the existing course, and the capstone is moved back behind them, so the course does not acquire a lesson the learner could open on day one and does not flip to `done` with the extension unwritten. No existing lesson is renumbered, re-stated or reset
- Every goal a subject has been extended to stays on its page with the lessons it added, so a second extension is a decision taken with the first one in view. A request that has been made and not yet planned says so rather than reading as one that added nothing
- AC: an extension adds only lessons the course does not already have, and no existing lesson's ordinal, state, content or edges change; AC: an extension is refused while a run is under way for that subject, and while the subject has no lessons to extend, with the reason stated; AC: the lessons an extension adds are unwritten until the ordinary writing pass is authorised, and the capstone sits behind them; AC: a requested detour becomes a new module authored via the same F6 sandboxed session contract, inserted as a new node in the module graph (with prerequisite edges where genuine) without disrupting already-completed modules' state; AC: user can decline/skip a completed detour without it counting against core-graph progress; AC: a detour never becomes a prerequisite of an already-existing module
- paths: happy (detour requested, generated, inserted, completed) / detour request during an already-`needs-attention` topic (declined until topic stabilizes, user informed why) / user abandons detour partway (core path progress unaffected) / subject extended to a further goal (extra lessons planned onto the end of the course, written by the ordinary pass) / extension asked for while a pass is running (declined, reason stated, nothing queued) / extension asked for before the subject has an outline (declined, pointed at planning) / research for an extension fails (the goal is split by subtopic instead, and the plan is named as a fallback rather than the press being lost) / the extension proposes lessons the course already has (dropped, and the room they would have taken goes to lessons that are missing)
- scale: detours per topic=3, lessons per extension=4-40 (sized from the goal)
- e2e: yes

## F13: Capstone project

- Each topic culminates in an authentic build (Dewey/Kilpatrick project method): an artifact or fully-specified design/solution the learner produces, spec'd by F2 from the topic's driving question and the learner's stated purpose (F1) — the "build in collaboration with AI agents" goal made concrete
- **The tutor proposes the project; the learner does not invent it.** The brief fixes the scenario and its givens — the case, data, system, documents or figures it works on are written into it — and exactly what gets built. The learner is never left to pick the project's subject or case, or to go and find the sources it is about; what is left to them is the building, the design decisions inside a problem the brief has already set, and any options they are offered are written out in full. Until a brief is written the project cannot be opened for review: the page says the tutor has not set it yet rather than asking what they built against a bare title. A brief rewritten after a review was opened replaces the old one in that review for as long as nothing has been handed in
- Sits in the module graph as a node with prerequisite edges on the modules its spec depends on; becomes available (advisory, like any node) when those pass
- Assessed via the F4 evaluator contract, adapted to work-review: Socratic chat over the submitted work, specific narrative feedback on shortfalls, revise-and-resubmit rather than re-ask; graduated hints and assist-level recording apply
- Completing it flips the topic from `modules-complete` to `done` (F5)
- AC: the capstone spec explicitly references the driving question and the learner's purpose; AC: the spec is a project the tutor set — it names its own case and givens, and never asks the learner to choose the project, its case or its sources; AC: a project with no written brief cannot be opened or handed in; AC: assessment judges the produced artifact/solution, not recall questions; AC: prior-round feedback remains visible across revisions; AC: a topic is not `done` until the capstone passes
- paths: happy (build, submit, pass) / submission falls short (specific feedback, revise, resubmit, pass) / learner purpose too vague for an authentic build (F2 falls back to a synthesis design problem spanning the topic's modules) / capstone attempted past the advisory with prereq modules incomplete / project opened before its brief is written (refused, the page says the tutor has not set it yet) / brief rewritten after the review was opened but before anything was handed in (the review's opening quotes the new brief)
- scale: revision rounds per capstone=5
- e2e: yes

## F14: Flash card library

- The one place in this app where knowing something by heart IS the material. Everywhere else recall is deliberately not rewarded — F4 judges understanding, F7 rewords rather than repeats, and F1 says outright that formulas abstracted away in practice are not worth memorising. Names are the exception: nothing derives "the $-\mathrm{COOH}$ group is called a carboxyl", and a learner who does not know it stops mid-sentence to look it up. So the flat facts get their own shelf rather than being smuggled into the module graph
- A **deck** is a set of cards with a name. It may hang off a subject the learner is studying (the flash cards for their organic chemistry course) or stand entirely on its own (a language's irregular verbs, a set of unit prefixes) — a learner may keep cards for something they are not taking a course in, and the library does not ask them to invent a topic first
- A **card** is two sides the learner wrote: a front they will be asked, and a back they have to remember. Cards are authored by hand, one at a time, or **pasted in as a list** — one card per line, split on the separator the learner's own list already uses (tab, spaced dash, colon, pipe, equals). A list of twenty functional groups copied out of a textbook is one paste, not twenty forms
- The paste is never guessed at and never silently trimmed: a line with no two sides is not turned into a one-sided card and not dropped either — it comes back named, so the learner can see the three lines that did not make it and fix the separator
- Both sides render as typeset math (F3's rule: LaTeX is typeset on every learner-facing surface, and a chemistry card is exactly where a subscript matters)
- Studying is **retrieval, not reading**: the front is shown alone and the back is withheld until the learner asks for it, then three buttons record how it went — didn't know it / knew it slowly / knew it
- Scheduling is F7's, unchanged: the same FSRS-6 memory model, the same three grades, the same day-scale intervals. A card is an item with a stability, a difficulty and a due date — which is precisely what FSRS was built for. What differs is only the signal: a module's grade is an evaluator's judgement, a card's is the learner's own read of the recall, which is the ordinary flashcard self-grade
- The memory state stays internal, exactly as it does for modules: what leaves the server is the card's two sides, when it is next due, and whether it has ever been answered. No stability, no difficulty, no percentage, nothing a learner could rank themselves by (F5)
- A new card is due immediately and sorts to the front of the queue — it has no interval it has earned yet. A deck is a queue and never a gate: nothing in the rest of the app is blocked by cards left unstudied, and nothing nags about them
- **A lesson may arrive with a pack of cards already written.** The session that plans and writes a lesson is the one thing in the system that knows which handful of names in it are flat facts — the ones nothing derives — so it may propose a small named set (up to 20 cards) alongside the lesson, with one line saying why they are worth knowing by heart. A lesson with no such facts proposes nothing rather than an empty pack, and a rule the learner should be able to work out never belongs in one
- The pack is an **offer, not a delivery**: it is shown with the lesson, both sides visible, and nothing reaches the learner's cards until they press the button. A deck that filled itself up behind them is a chore they never chose. Taking it makes a deck named by the lesson and attached to that subject, which is then an ordinary deck in the library — renameable, editable, deletable, studied with everything else
- Taking the same pack twice adds nothing twice: the cards already in that deck are left exactly as they are, schedules included, and the lesson says how many were new and how many were already there. A lesson rewritten with two extra cards adds only those two
- Editing a card's text does not touch its schedule. Correcting a typo is not a retrieval, and rewriting the memory state would hand out a fresh interval for a spelling fix
- AC: the back of a card is not in the page until the learner reveals it, and the three answer buttons are not offered before the back is shown; AC: a card answered "knew it" comes back later than the same card answered "didn't know it", and a missed card is counted as a lapse; AC: no stability, difficulty or retrievability value appears in any API response or anywhere in the UI, and no card surface expresses a proportion or a score; AC: every line of a paste either becomes a card or is named in the skipped list — none is dropped and none is truncated; AC: a card whose text is edited keeps its due date and its memory state exactly; AC: deleting a deck deletes its cards and leaves every other deck whole; AC: a deck may be created with no subject attached, and a deck naming a subject that no longer exists is refused rather than orphaned; AC: a lesson's card pack is never added to the library without the learner asking, and adding the same pack again creates no second deck, no duplicate card and moves no card's due date; AC: a lesson that proposed no pack shows no card section at all
- paths: happy (make a deck, paste a list, study it) / a single card typed in by hand / a paste where some lines have no separator (cards made from the rest, the others named) / a paste that splits into nothing (the box is left filled so the learner can fix it) / studying with nothing due (an empty queue stated as a normal place to be, not an error) / a card edited mid-schedule (text changes, schedule does not) / a deck attached to a subject the learner later deletes / a card answered while the app cannot save it (the answer is reported as unsaved and the learner's place in the round is kept) / a lesson proposes a pack and the learner takes it (a deck on the subject, made on the click) / the same pack taken a second time (nothing added, nothing moved, said plainly) / a lesson that proposes no pack (no card section on the page) / a pack the app cannot save (reported, the cards stay on the page)
- perf: study queue start <300ms p95; a paste of 500 lines lands in one write
- scale: decks=100, cards per deck=1000, cards per paste=500, cards per study round=60, cards per lesson pack=20
- e2e: yes
